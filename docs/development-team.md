# HomeCierge 개발팀 운영 계획안

`codex/backend-foundation`에서 총괄이 작업을 지시하고 최종 리뷰를 맡는다. 2026-11-26부터 총괄은 Codex에서 Claude로 바뀌었고, 구현 워커는 Antigravity의 Gemini 4 Neon(XHigh)이 맡는다. 그 전까지는 Codex가 총괄하고 Claude Opus 5.5 에이전트가 구현과 독립 검증을 맡았다. 첫 목표는 화면 없이 한 공고·한 주택형의 요청이 수집, 정규화, 저장, 비교, 결과 조회까지 이어지게 하는 것이다. 개발 순서와 제품 판단의 근거는 [전체 개발 계획](development-plan.md)과 [현행 PRD](prd/01-product-prd.md)을 따른다.

## 누가 무엇을 맡는가

총괄(2026-11-26부터 **Claude**, 그 전에는 **Codex**)이 작업마다 목표, 담당자, 편집 범위와 수락 예시를 정한다. 구현자의 결과와 독립 검증 결과가 다르면 실제 변경분과 재현 사례를 확인해 수정을 지시한다. 기술 선택과 브랜치 반영은 총괄이 맡고, 사용자에게 보이는 제품 규칙을 새로 정해야 할 때는 영향 사례와 선택지를 사용자에게 전달한다.

| 맡을 역할 | 책임과 인계할 결과 | 처음 투입할 시점 |
| --- | --- | --- |
| 백엔드·서비스 API | 화면이 호출하는 요청과 응답 형식, 인증, 실행·조회·취소를 담당한다. 단위, 오류, 결과 상태와 사유가 담긴 계약을 프론트엔드에 넘긴다. | BE-01 계약 초안 |

| 비교 로직·자료 검증 | 공식 자료로 단지·공급면적 대응이 가능한지 확인하고, 지역 확대·단지 선정·거래 종류별 통계를 구현한다. 보류 이유와 판정 예시를 QA에 넘긴다. | BE-01 자료 조사, BE-05 비교 구현 |
| DB·플랫폼 | Supabase 스키마, 행 수준 보안(RLS), 계정별 접근, 작업 저장·복구, Vercel 환경을 맡는다. 마이그레이션과 계정 두 개를 사용한 권한 검사를 함께 인계한다. | BE-02 저장 계약 검토, BE-03 구현 |
| 프론트엔드 연동 | 합성 응답으로 화면팀이 사용할 예시를 만들고 인증·재조회·오류 처리를 검증한다. 화면을 인계받으면 실제 사용자 흐름을 연결한다. | BE-01 초안 검토, BE-02 모의 응답 |
| 디자인·사용자 경험(UX) 검수 | 청약 초보자가 보류 이유와 다음 행동을 이해할 수 있는지 살핀다. 상태별 문구와 출처·단위 표시 기준을 별도 화면팀에 전달한다. 화면팀이 제작한 구성과 시각 디자인을 인계받을 때 프레임워크와 실제 표시 동작을 함께 확인한다. | 첫 합성 응답, 이후 화면 인계 시점 |
| AI·보고서 | 저장된 결과와 근거로 설명·보고서를 만들고, 화면·대화·PDF의 수치를 대조한다. 서비스용 모델의 근거 일치도·지연·비용을 비교한다. | 결과 스냅샷과 비교용 예시가 준비될 때 |
| 독립 품질 검증(QA) | 구현자가 작성한 코드와 별도로 PRD에서 기대 결과를 도출한다. 대표 사례와 실패 사례를 실행해 차이, 재현 방법, 검증한 범위를 총괄에 전달한다. | BE-01부터 작업별 참여 |

## 한 브랜치에서 어떻게 협업하는가

1. **총괄이 작업을 나눈다.** 지시서에 관련 요구·수락 기준, 입력과 기대 결과, 수정할 파일, 다음 담당자가 받을 결과를 적는다. 같은 브랜치에서 파일별 편집자를 한 명씩 정한다. 공통 타입이나 마이그레이션처럼 편집 범위가 겹치면 선행 변경을 먼저 검토하고 다음 작업을 배정한다.
2. **필요한 역할을 병렬로 배정한다.** 2026-11-26부터 Orca 워커는 기능마다 별도 하위 워크트리에서 `--worktree new-child --agent antigravity --model gemini-4-neon-xhigh`로 배정한다. Antigravity 모델 ID에는 추론 강도가 포함되므로 `--effort`를 따로 넣지 않는다(`agy models`로 확인). Gemini 사용량이 소진되면 같은 지시서와 워크트리를 유지한 채 Orca Claude 에이전트(`--agent claude --model claude-opus-5-5 --effort xhigh`)로 인계한다. Antigravity의 `claude-opus-5-5-high`는 서드파티 한도가 금방 소진돼 인계 순서에서 뺐다. 어느 워커의 결과든 총괄이 검수한다. 워커는 자기 브랜치에 커밋하고 총괄이 검토해 기준 브랜치에 합친다. 이전에는 현재 작업 폴더에서 `--agent claude --model claude-opus-5-5 --effort xhigh`, 대체로 `--agent codex --model gpt-6.2-sol --effort max`를 썼다. 총괄은 배정한 모델·강도와 세션의 표시값을 대조한다. 서비스용 모델은 [PRD의 모델 선정 기준](prd/01-product-prd.md#76-llm-선택과-비교-기준)에 따라 평가한다.
3. **구현과 검증 결과를 받는다.** 구현자는 바꾼 파일, 달라진 동작, 검사 명령과 결과, 남은 의문을 전달한다. QA는 합성 입력과 기대값을 독립적으로 정하고 통합된 코드에서 결과를 확인한다. 실자료는 출처별 이용 조건을 확인한 범위에서 다루고, 실제 인증·외부 API로 검수한 결과는 오프라인 검사와 구분해 기록한다. [데이터 취급 원칙](data-handling.md)
4. **총괄이 최종 리뷰하고 반영한다.** 실제 변경분을 기존 호출 경로와 PRD에 대조하고, 실패했거나 증거가 부족한 사례는 직접 확인한 뒤 담당자에게 돌려보낸다. 검수를 마친 작업은 총괄이 `codex/backend-foundation`에 모아 커밋·푸시하고, 새 마이그레이션은 서울 개발 DB에 적용해 타입을 다시 생성하며, 작업자 코드가 바뀌면 개발 Mac 서비스를 재설치한다(2026-11-26 사용자 승인). Production은 포함하지 않는다. 팀별 결과를 비교할 때 이 브랜치의 변경분과 검수 결과를 함께 제시한다.

## 첫 작업 BE-01을 어떻게 시작하는가

총괄이 아래 네 작업을 동시에 배정한다. API 계약 문서, 응답 처리 코드, 자료 조사 기록, 테스트의 편집자를 각각 분리한다.

| 누가 맡는가 | 처음 수행할 일 | 총괄이 확인할 결과 |
| --- | --- | --- |
| 백엔드·서비스 API | 실행 상태, 결과의 완전성, 항목별 보류 이유를 구분하고 금액·면적·오류 형식을 정의한다. | 계약 초안(v0)과 같은 요청에 대한 정상 0개·부분 수집·조회 실패 합성 응답. 기존 조회 경로 `/api/health`, `/api/ready`, `/api/v1/me`의 호환성을 확인한다. |
| 외부 API·데이터 정규화 | [인증값 정제 결함 F-11](prd/03-review-resolution.md)을 다룬다. 조회 도구와 그 호출 경로에서 응답 해석과 저장·로그 출력을 분리한다. | 짧은 합성 인증값과 일반 데이터의 일부가 같아도 JSON·XML의 필드와 값이 보존되고, 저장·로그에 반향된 인증값은 가려진다. |
| 비교 로직·자료 검증 | V1~V4 조사를 시작한다. 공급면적·권리 거래 식별, 공고 PDF·정정판, 지역·기간, 출처별 이용 조건을 점검한다. | 항목별 근거, 확인된 범위, 미확인 사유와 다음 조사. 공급면적은 검토한 후보 수와 확인·불일치·보류 수를 함께 기록한다. |
| 독립 QA | 짧은 합성 인증값과 인코딩·이스케이프 사례를 준비한다. 정상 0건, HTTP 200 안의 업무 오류, 페이지 누락에 대해 기대값을 먼저 적는다. | F-11을 재현하는 검사와 수정 후 결과, 서로 다른 상태가 빈 배열 하나로 합쳐지지 않는다는 계약 검사. |

첫 공동 리뷰에서는 **같은 동에 확인된 단지가 0개이고 필요한 거래 페이지 하나가 누락된 사례**를 사용한다. 수집기는 누락을 기록하고 API는 부분 수집 사유를 전달해야 한다. 프론트엔드·디자인 담당은 이를 받은 사용자가 ‘이 동에는 비교할 단지가 없다’고 오해할 표현이 있는지 확인한다. BE-01에서는 상태를 전달할 수 있는지 검수하고, BE-05에서는 같은 입력으로 엔진이 지역 확대를 보류하는지 검증한다. 해당 제품 기준은 A-06·A-10이다. [PRD 수락 시나리오](prd/01-product-prd.md#121-구현-후-수락-시나리오)

## 이후 어떤 역할로 넘기는가

| 개발 시점 | 주 담당과 인계 내용 |
| --- | --- |
| BE-02 공고·거래 정규화 | 외부 API 담당이 합성 응답과 정규화 결과를 넘긴다. DB 담당은 저장할 단위·식별자·근거를, 프론트엔드 담당은 같은 형식의 화면용 모의 응답을 확인한다. |

| 공고·탐색·보고서·보조 기능과 화면 인계 | 외부 API 담당이 공고·문서·부가 자료를, AI·보고서 담당이 결과 설명을 확장한다. 프론트엔드·디자인 담당은 초기 합성 예시부터 별도 화면팀과 공유하고 화면 인계 후 실제 인증·승인·저장·삭제 흐름을 함께 검수한다. [화면팀 연결 계약](frontend-handoff.md) |
