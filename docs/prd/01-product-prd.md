# HomeCierge PRD 초안 v0.1

사용자가 선택한 청약 공고와 주택형을 기준으로, **같은 동의 아파트 실거래를 먼저 비교하고 비교 대상이 정상 조회로 0개일 때 같은 구로 확대**한다. 공고 가격·면적·납부 일정과 비교 자료의 출처를 함께 제시하고, 확인되지 않은 내용은 보류 사유로 보여준다. 여러 채팅을 유지하며 공유 프로필은 사용자가 변경안을 확인한 뒤 갱신한다.

이 문서는 2026-11-09까지의 사용자 결정과 저장된 검증 결과를 반영한 제품 요구사항 문서(PRD) 초안이다. 기존 5km 요구를 대체하며, 과거 호가·임시 세션 중심 초안보다 이 문서를 우선한다. 현재는 데이터 접근·일부 연결 로직의 검증 단계다. 서비스 화면, 새 동→구 검색 흐름, 공급면적 기반 최종 비교, 사용자 프로필 기능은 구현 완료 상태가 아니다.

## 1. 요구사항과 검증 상태를 구분한다

두 상태를 독립적으로 관리한다. 요구사항이 확정됐다는 이유로 기능을 검증 완료로 표시하지 않고, API 호출이 성공했다는 이유로 출시 기능을 임의 확정하지 않는다.

| 요구 상태를 구분한다 | 의미를 정의한다 |
| --- | --- |
| **확정** | 기존 사용자 요구와 이번 변경에서 유지·확정한 동작. 변경하려면 다시 합의한다 |
| **설계 제안** | 확정 요구를 구체화하기 위한 초안. 채택된 기본값이나 개발 완료로 취급하지 않는다 |
| **미정** | 결정 ID(D-01~D-07)로 추적한다. 필요한 기능을 임의 값으로 완성하지 않는다 |
| **후속 / 제외** | 후속 단계로 미룬 기능 또는 현재 제품 범위에서 제외한 기능 |

검증 상태는 **실응답 확인**, **제한된 사례·로직 검증**, **미구현·미검증**으로 구분한다. 아래 E-01~E-06은 검증 근거, R-01~R-14는 확정 요구, P-01~P-06은 설계 제안, A-01~A-17은 구현 후 수락 기준이다. 수락 기준의 구체화는 초안이며 테스트 통과를 뜻하지 않는다.

## 2. 문제와 사용자 가설을 정의한다

핵심 문제는 공고·실거래·단지 정보의 면적, 가격 의미, 적용 시점, 식별자가 달라 사용자가 직접 맞춰 봐야 한다는 점이다. 제품은 공고와 주변 비교 자료를 같은 조건으로 정리하고, 확인된 사실과 부족한 근거를 구분하도록 돕는다.

초기 사용자 가설은 **관심 청약의 분양가와 구매 준비 사항을 검토하려는 사람**이다. 신혼부부·첫 주택 구매자 등 세부 타겟, 문제의 빈도와 중요도는 사용자 조사로 검증되지 않았으며 D-05에서 정한다. API 검증은 사용자 가치 검증을 대신하지 않는다.

사용자가 얻을 결과는 다음과 같다.

- 어떤 공고·주택형·지역·기간·면적 기준을 비교했는지 확인한다.
- 단지별 실제 거래 통계와 분양가의 의미를 구분해 읽는다.
- 필수 추가 비용·납부 일정·공고 조건을 원문 위치와 함께 확인한다.
- 결과가 없거나 불완전한 이유를 알고, 필요한 조건 변경을 직접 선택한다.
- 이전 채팅과 확인한 프로필을 이어서 사용한다.

법령·ODsay·건축물대장 API를 확보한 것은 확정된 작업 결과다. 이 사실만으로 자동 자격 판정, 모든 후보의 출퇴근 사전 계산, 세금·대출 계산을 초기 기능으로 추가하지 않는다.

## 4. 사용자 흐름을 제안한다

다음 흐름은 **설계 제안 P-01**이다. 초기에는 한 공고·한 주택형의 검토를 완결하는 안을 제안하며, 동시 분석 건수와 조건 기반 공고 발견 포함 여부는 D-04에서 결정한다.

| 단계를 진행한다 | 제품이 보여줄 결과를 정한다 | 사용자가 선택하거나 확인한다 |
| --- | --- | --- |
| 1. 채팅을 시작·재개한다 | 기존 채팅 목록과 이번 분석에 적용할 확인된 조건 | 다른 채팅으로 이동하거나 새 분석 시작 |
| 2. 공고를 정한다 | 선택한 공고의 이름·식별자·주소·접수 상태·공식 출처 | 공고·PDF·직접 입력 경로와 동명 공고의 구별. 입력 UI는 D-04에서 확정 |
| 3. 주택형과 조건을 정한다 | 공급/전용면적, 기본 가격 또는 가격 범위, 거래 기간·종류 | 주택형·호실/가격 적용 방식 선택. 필요한 정보가 모호하면 확인 |
| 4. 비교 대상을 찾는다 | 같은 동 후보, 정상 0개이면 같은 구 후보, 적용 범위·보류 사유 | 기본 동→구 확대에는 추가 확인 불필요. 그 밖의 조건 변경·직접 지정은 확인 |
| 5. 결과를 읽는다 | 단지별 통계, 본체 가격·필수 옵션·납부 일정, 지역 뉴스와 근거 | 원문 확인, 후보·조건 변경 요청 |
| 6. 프로필 변경을 검토한다 | 최근 대화에서 추출한 변경 항목의 이전 값·새 값·근거 | 승인·거절·취소. 승인 전 공유 프로필 유지 |
| 7. 다시 검토한다 | 변경된 조건으로 생성한 새 결과와 적용 시점 | 다른 채팅·기존 결과와 혼동하지 않도록 분석 조건 확인 |

공고 최고금액이 예산을 넘는다는 이유만으로 공고 전체를 부적합 처리하지 않는다. 다른 주택형·호실 가격을 확인하지 못했다면 가격 조건은 미확인으로 남긴다. 접수가 종료된 검증 사례는 현재 신청 가능한 공고처럼 제시하지 않는다.

## 6. 동→구 검색 규칙을 정의한다

### 6.1 비교 가능성과 정상 0개를 구분한다

‘매물’은 이 제품에서 비교할 아파트 단지를 뜻한다. 호가 매물 수가 아니라 **선택한 거래 종류·기간·면적 조건을 충족하는, 해제를 제외한 거래가 있고 단지 식별이 확인된 후보**를 판단한다. 최소 거래 건수 임계값은 미정이다. 임의로 ‘3건 이상’ 같은 조건을 도입해 동의 후보를 0개로 만들지 않는다.

면적 대응 자료가 없는 후보는 ‘면적 불일치’가 아닌 ‘미확인’이다. 다른 회차 PDF, 주소 충돌, 단지 연결 보류, 부분 수집, 인증/통신/업무 오류도 정상 0개와 구분한다. K-apt 목록 97/97개 확보는 해당 API 목록의 완전성이지 동 안의 모든 비교 가능 단지가 없다는 증거가 아니다.

**정상 0개**는 요청한 지역·기간·거래 종류에 필요한 조회와 판별이 끝나고, 후보의 존재 여부를 바꿀 미확인 사항 없이 비교 대상이 0개인 상태다. ‘0개로 확인됨’과 ‘확인된 후보가 아직 0개임’을 구분한다. 동의 정상 0개가 증명되지 않으면 자동 구 확대를 실행하지 않는다.

### 6.2 결과 범위와 동작을 정한다

| 관찰한 상태를 확인한다 | 적용할 범위를 정한다 | 결과와 다음 행동을 정한다 |
| --- | --- | --- |
| 대상 동·구 식별 불가 | 미확인 | 주소·지역을 확인한다. 이름 추측이나 좌표 반경으로 대체하지 않음 |
| 동에 확인된 후보 1~5개 | 같은 동 | 해당 후보만 제시. 구에서 수를 채우지 않음 |
| 동에 확인된 후보 5개 초과 | 같은 동 | D-03에서 정한 기준으로 최대 5개 선정. 현재 초안에 거리순 기본값은 없음 |
| 동에 확인된 후보가 있고 미확인 후보도 있음 | 같은 동 | 확인된 결과와 미확인 수·사유 제공. 완전한 후보 목록·순위라고 표시하지 않음 |
| 동의 확인된 후보 0개, 미확인 후보 또는 미완료 조회 있음 | 같은 동의 판정 보류 | 구로 자동 확대하지 않고 누락·실패를 설명하거나 보완 |
| 동이 정상 0개 | 같은 구 전체 | 추가 승인 없이 확대하고 동→구 변경과 이유 표시 |
| 구에서 후보 확인 | 같은 구 | 최대 5개와 구 범위·조건 표시. 미확인 후보가 있으면 함께 고지 |
| 구도 정상 0개 | 같은 구에서 종료 | 현재 조건의 비교 자료 부족 안내. 인접 구·기간·면적 자동 확대 없음 |
| 구 조회 실패·판정 미완료 | 같은 구의 판정 보류 | ‘구에도 없음’으로 표시하지 않음 |

지역 판정은 실거래 `sggCd`·`umdCd`와 주소의 법정동코드 등 검증된 코드를 사용한다. 행정동명·동일 이름·좌표 거리로 동·구를 대체하지 않는다. 법정동은 현재 데이터와 맞춘 설계 기준이며 구가 없는 지역의 대체 범위는 D-02에서 결정한다.

사용자 표시 문구의 예시는 다음과 같다.

- ‘구의동에서 비교 가능한 단지 2개를 확인했습니다.’
- ‘구의동 내 비교 가능한 단지가 없어 광진구로 확대했습니다.’
- ‘구의동의 일부 후보는 면적 정보를 확인하지 못해 비교 가능 여부를 판단 중입니다.’
- ‘현재 기간·면적 조건에서 광진구의 비교 자료를 찾지 못했습니다.’ — 구의 정상 0개일 때만 사용.

직접 지정한 단지의 지역 제한과 자동 후보 목록에 합치는 방식은 미정이다. 직접 지정 지원을 근거로 다른 구를 자동 검색하거나 기본 동→구 규칙을 무시하지 않는다.

**재현 근거를 찾는 위치**

아래 `api-evidence/`·`pdf-evidence/`는 원 프로젝트의 비공개 로컬 증거 경로이며 이 저장소에 포함하지 않는다. 검증 수치·해시는 [증거 색인](../api/evidence-index.json), 공개 코드의 재현 범위는 [개발 안내](../development.md)에 기록한다. 외부 API 원문 재배포 권한을 뜻하지 않는다.

- E-01: `docs/api/live-manifest.json`, `docs/api/live-manifest-20261109.json`, `api-evidence/20261106_live/`. 10서비스·14조회는 두 manifest의 합집합이다.
- E-02: `pdf-evidence/2026930040/reviewed-facts.json`, `combined.json`, `validation.json`.

## 8. 데이터·계산·실패 처리의 계약을 제안한다

데이터 보존 원칙은 기존 검증에서 이어받고, 아래 객체 구분과 필드 구성은 구현을 위한 설계 제안이다. 저장소나 프레임워크를 확정하지 않는다.

| 객체를 구분한다 | 보존할 내용을 정한다 | 잘못된 결합을 차단한다 |
| --- | --- | --- |
| 공고·주택형 | 공고/주택관리/모델 식별자, 유형·접수 상태, 면적 종류, 가격의 적용 대상, 원문·PDF 페이지 | 배열 순서·단지명만으로 병합하지 않음. API 최고금액을 개별 호실 가격으로 일반화하지 않음 |
| 분석 조건 | 공고·주택형·거래 종류·기간·면적 기준·실제 적용 동/구·확대 사유·후보 선정 규칙 버전 | 다른 지역·기간·주택형 통계를 같은 비교값처럼 섞지 않음 |
| 거래 스냅샷 | 원문, 요청 지역/월/페이지, 수집 시각·해시, 전체 건수·완료 상태, 단위·계약일·해제/정정 상태 | 만원→원 변환 근거 보존. 이름·날짜·층·가격이 같다고 동일 거래로 제거하지 않음 |
| 단지 연결 | 출처별 ID, 법정동·지번·도로주소, 연결 근거·충돌·보류 사유, 면적 대응 근거 | 다른 지역의 동명 단지, 같은 지번의 여러 단지를 임의 연결하지 않음 |
| 보충 근거 | 법령 MST·시행일·공포일, 뉴스 제목/발췌/URL/시각, 경로의 요청 조건·조회 시점 | 과거 공고에 현행 법령을 자동 적용하지 않음. 발췌를 전문으로 표시하지 않음 |
| 대화·프로필 | 채팅별 메시지·분석 참조, 확인된 프로필 버전, 변경 제안·승인 상태·근거 | 제안 상태의 값을 공유 프로필에 반영하지 않음. 다른 채팅의 결과 조건을 조용히 변경하지 않음 |

출처 값과 계산값을 구분하고 계산식·입력 참조를 보존한다. 공급면적 대응이 검증되지 않으면 전용면적 시험 통계를 공급면적 기준 비교표에 넣지 않는다. 가격 차이는 어떤 본체 가격/옵션 소계와 어떤 단지 통계를 비교했는지 표시해야 하며 확정 수익으로 표현하지 않는다. 계산식·대표값·비율 표시 방식은 D-03에서 구체화한다.

| 데이터 상태를 구분한다 | 화면에서 전달할 의미를 정한다 | 계산·검색에서 처리한다 |
| --- | --- | --- |
| 확인됨 | 출처와 적용 조건을 확인한 값 | 비교 입력 조건 충족 시만 사용 |
| 정상 0건 | 필요한 조회·판별을 완료했으나 대상 없음 | 동 단계에서만 같은 구 자동 확대. 구 단계면 자료 부족 |
| 일부 수집 | 페이지 누락·전체 건수 변경 등 | 전체 통계·후보 순위 확정 및 0개 판정 보류 |
| 미제공·미확인 | 필드 없음·빈 값·대응 근거 없음 | 0원·0분·조건 불충족으로 대체하지 않음 |
| 조회 실패 | 인증·네트워크·업무 오류 | 재시도/보완 가능성과 독립적으로 확인한 결과 제공 |
| 연결 보류·출처 충돌 | 여러 후보·주소 차이·다른 집계 값 | 양쪽 근거 보존, 대표값 임의 선택 금지 |

실제로 K-apt는 HTTP 200 안에 API 오류 04가 있었고, ODsay는 근거리 요청 오류 -98과 `totalWalkTime=-1`을 반환했다. 각각 조회 성공·0분 경로로 취급하지 않는다. ODsay -1은 도보시간 미제공으로 보존한다.

## 9. 운영과 검수의 조건을 정한다

- API 키는 서버 측 비밀정보로 관리하고 클라이언트·보고서·일반 로그·공유 산출물에 포함하지 않는다. 사용자 비밀번호·OTP를 대화로 받지 않는다. 인증값과 계정별 운영 기록은 로컬에서 관리하며 이 저장소에 포함하지 않는다.
- 공고 PDF의 자동 추출 결과와 검수한 값을 구분한다. 원문 회차·페이지 확인에 실패하면 해당 항목을 보류하며, 다른 항목의 검증된 결과는 제공한다. 스캔·복잡한 표·정정 공고의 검수 방법은 추가 검증한다.
- ODsay는 현재 등록된 서버 환경의 소량 호출 성공만 확인했다. 배포 IP, 대량 사전 계산, 결과 저장·재사용 허용 범위는 운영 전 확인한다. 로컬 진단 증거의 장기 보관 허용도 미확인이다. [ODsay 이용약관 4.5.10](https://lab.odsay.com/doc/totalPolicy)
- NAVER 뉴스의 계정 상세 과금·운영 한도, 본문 수집·LLM 입력·표시·보관 범위는 별도 확인한다. OpenAI는 키 설정 존재만 확인했고 모델 인증·정확도·성능·비용을 검증하지 않았다.
- 프로필·업로드 파일·대화의 보관/삭제·접근 통제와 서비스 성능·비용 상한은 D-06·D-07에서 정한다. 운영 목표 수치를 임의로 선언하지 않는다.

| 결정 ID를 추적한다 | 이미 고정된 조건을 확인한다 | 결정할 내용을 구체화한다 | 다음 작업에 미치는 영향을 적는다 |

| D-06 대화·프로필·기술 | 다중 채팅 지속, 확인 후 프로필 갱신 | 인증·접근 범위·저장/삭제·분석별 조건, 동시 변경·버전, 기술 스택·모델·검수 UX | 대화 일관성과 개인정보 처리·재현성 결정 |

우선순위는 **D-01 → D-02·D-03 → D-04**를 제안한다. 공급면적 비교의 성립 조건을 먼저 정해야 ‘동에 비교 대상이 없다’는 판정을 설계할 수 있기 때문이다. 원문·근거·실패 상태의 구조화와 대화 흐름 설계는 이 결정 작업과 함께 진행할 수 있다.

## 12. 개발 순서와 남은 위험을 연결한다

| 순서를 제안한다 | 작업 결과를 정의한다 | 넘어가기 위한 조건을 확인한다 |
| --- | --- | --- |
| 1. 비교 규칙 확정 | D-01~D-04와 한 공고·한 주택형의 수작업 기준 결과 | 공급면적 대응과 정상 0개 판정, 기간·선정·첫 흐름의 미정값 해소 |
| 2. 데이터 연결 | 공고/API/PDF·거래·단지의 출처·단위·식별·실패 상태 계약 | 다른 회차·부분 수집·해제·출처 충돌을 재현 가능하게 처리 |
| 3. 동→구 및 비교 | 지역 상태별 흐름, 면적 기반 후보, 최대 5단지의 통계·보류 표시 | A-03~A-13을 새 정책으로 검증. 과거 반경 검사로 대체하지 않음 |
| 4. 채팅·프로필·보고서 | 다중 채팅과 확인 흐름, 공고·비교·뉴스·근거 결과 연결 | A-14~A-17 및 공고/가격 근거 표시 검증 |
| 5. 보조 기능·운영 | 채택된 법령·출퇴근·자금 기능, 기능별 이용 조건·배포 준비 | D-06·D-07 해소, 채택 기능의 추가 수락 기준 검증 |

현재 가장 큰 공백은 공급면적 대응 자료다. 이 자료가 없으면 주소가 연결된 후보도 최종 비교 가능으로 확정할 수 없다. K-apt 오류·자료 범위·대표 주소 차이는 정상 0개 판정의 완전성을 제한한다. 서로 다른 공고 서식·정정 공고, 동→구 자동 확대, 사용자 대화와 프로필 변경은 별도 구현 검증이 필요하다.
