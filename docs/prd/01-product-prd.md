# HomeCierge PRD v1.0 — 제품 요구 기준본

첫 사용부터 로그인한 사용자의 **희망 지역·예산으로 청약 공고를 찾고, 한 공고·한 주택형을 분석·비교**한다. 공급면적·입주 월 범위는 선택 조건이며, 예산은 분양가+필수 옵션과 대조한다. **같은 동·읍·면의 실거래를 먼저 비교하고 정상 0개일 때 같은 구, 구가 없으면 같은 시·군으로 확대**한다. 공급면적 대응이 확인된 후보만 비교하고 미확인은 구분한다. 자금표·법령 근거·대중교통 및 자동차 경로, 계정의 다중 채팅·확인 후 공유 프로필 갱신, 보고서 저장·PDF 다운로드를 초기 제공 범위로 한다.

이 문서는 **2026-11-10까지 확정한 사용자 결정 36개**와 2026-11-09까지 저장된 검증 결과를 반영한 제품 요구사항 문서(PRD) 기준본이다. 기존 5km 요구와 호가·임시 세션 중심 초안보다 이 문서를 우선한다. 요구 확정과 구현·출시 검증은 별개다. 현재는 데이터 접근·일부 연결 로직 검증 단계이며 제품 기능은 구현 완료 상태가 아니다. 사용자 결정은 [결정 기록](02-decision-log.md), 리뷰 처리 상태는 [보완 추적표](03-review-resolution.md), 남은 설계·자료 검증은 §10·§12에서 추적한다.

2026-11-11 사용자가 데이터베이스·배포 기반으로 **Supabase와 Vercel**을 선택했고 화면은 별도 팀이 제작한다. 개발 DB의 스키마·소유권·프로필 승인 함수 적용, 원격 권한 검사 및 인증 조회 API의 Preview 배포 상태는 [인프라 문서](../infrastructure.md)에서 추적한다. 실제 Auth·화면 통합과 제품 수락 검증 완료를 의미하지 않으며 아래 E-01~E-06의 과거 근거는 유지한다.

## 1. 요구사항과 검증 상태를 구분한다

두 상태를 독립적으로 관리한다. 요구사항이 확정됐다는 이유로 기능을 검증 완료로 표시하지 않고, API 호출이 성공했다는 이유로 출시 기능을 임의 확정하지 않는다.

| 요구 상태를 구분한다 | 의미를 정의한다 |
| --- | --- |
| **확정** | 기존 사용자 요구와 이번 변경에서 유지·확정한 동작. 변경하려면 다시 합의한다 |
| **설계 제안** | 확정 요구를 구체화하기 위한 초안. 채택된 기본값이나 개발 완료로 취급하지 않는다 |
| **미정** | 결정 ID(D-01~D-07)로 추적한다. 필요한 기능을 임의 값으로 완성하지 않는다 |
| **후속 / 제외** | 후속 단계로 미룬 기능 또는 현재 제품 범위에서 제외한 기능 |

검증 상태는 **실응답 확인**, **제한된 사례·로직 검증**, **미구현·미검증**으로 구분한다. 아래 E-01~E-06은 검증 근거, R-01~R-18은 확정 요구, P-01~P-06은 설계 제안, A-01~A-59는 구현 후 수락 기준이다. 수락 기준은 제품 검수 계약이며 테스트 통과를 뜻하지 않는다.

## 2. 문제와 사용자 가설을 정의한다

핵심 문제는 공고·실거래·단지 정보의 면적, 가격 의미, 적용 시점, 식별자가 달라 사용자가 직접 맞춰 봐야 한다는 점이다. 제품은 공고와 주변 비교 자료를 같은 조건으로 정리하고, 확인된 사실과 부족한 근거를 구분하도록 돕는다.

초기 설명과 기본 사용 흐름의 우선 대상은 **청약 경험이 적고 실거주할 첫 집을 마련하려는 사람**으로 확정했다. 주거·예산 조건에 맞는 공고를 찾고, 분양가와 구매 준비 사항을 근거와 함께 검토하도록 돕는다. 공급면적/전용면적, 분양가 소계/별도 비용, 공고 접수 상태/개인 자격의 차이를 읽을 수 있게 설명한다. 다른 사용자의 이용을 제한하지 않는다.

이 대상 선정은 제품 설계 결정이며, 문제의 빈도·중요도와 사용자 가치는 아직 조사로 검증하지 않았다. 신혼 여부 등 추가 세부 타겟을 임의로 제한하지 않으며, 사용자 조사와 성공 지표는 D-05에서 구체화한다. API 검증은 사용자 가치 검증을 대신하지 않는다.

사용자가 얻을 결과는 다음과 같다.

- 희망 지역·예산과 선택 조건을 바탕으로 공고를 찾고, 실제 적용 조건과 미확인 사항을 확인한다.
- 어떤 공고·주택형·지역·기간·면적 기준을 비교했는지 확인한다.
- 단지별 실제 거래 통계와 분양가의 의미를 구분해 읽는다.
- 필수 추가 비용·납부 일정·공고 조건을 원문 위치와 함께 확인한다.
- 입력한 자금과 납부 일정을 대조하고, 공고 조건의 법령 근거와 지정 목적지의 출퇴근 경로를 확인한다.
- 결과가 없거나 불완전한 이유를 알고, 필요한 조건 변경을 직접 선택한다.
- 이전 채팅과 확인한 프로필을 이어서 사용한다.

## 3. 제품 범위를 정리한다

| 범위를 구분한다 | 포함하거나 제한할 내용을 적는다 | 상태를 표시한다 |
| --- | --- | --- |
| 공고·주택형 | 아파트 신규분양·무순위·잔여세대·재공급. 한 번에 한 공고·한 주택형 분석. 공식 PDF 자동 확보 후 실패 시 업로드 보완, 자동 점검을 통과한 상세 값 사용 | 초기 범위·확보·검수 방식 확정. 유형별 필드·서식·자동 점검 검증은 별도 |
| 비교 | 같은 동·읍·면 우선→전체 정상 0개면 구 또는 구 없는 시·군. 고유 주변 최대 5단지, 공급면적 ±5% 안에서 차이순·직선거리순. 최근 1년 및 사용자 기간. 자체 거래 별도 | 확정. 대응 자료·복수 대응·윤일 경계·대표 좌표 등은 설계·검증 대상 |
| 가격 자료 | 매매·분양권·입주권 거래를 분리하고 해제를 제외. 선택 주택형은 확인된 호실들의 분양가+필수 옵션 최소~최대 범위로 표시하며 특정 호실 선택 시 그 가격으로 비교 | 확정. 일부 호실만 확인된 범위와 전체 범위 구분 |
| 결과 | 공고 요약·비교표·지역 뉴스·보조 기능·근거·수집 시점·누락 사유. 서비스 내 저장·다시 열기와 PDF 다운로드 | 초기 제공 범위 확정. 화면·PDF 구성은 상세 설계 대상 |
| 대화·프로필 | 첫 사용부터 로그인, 계정 저장·기기 간 이용. 탐색 조건·목적지는 확인 후 공유, 자금은 분석별 저장. 사용자 입력은 삭제할 때까지 보관하고 개별·계정 삭제 지원 | 제품 정책 확정. 인증 수단·삭제 처리·동시 변경의 상세 설계는 미정 |
| 보조 기능 | 기초 자금표, 법령 근거 탐색, 대중교통·연결 도보·자동차 출퇴근 경로 조회 | 모두 초기 범위 확정. 자동차 경로 데이터 출처·연동을 포함한 검증은 별도 |
| 후보 공고 발견 | 시·군·구·예산 필수, 공급면적·입주 월 범위 선택. 접수 중 마감일순→예정 시작일순. 충족 목록과 확인 필요 목록을 기본 분리 제공. 종료는 선택 시 포함 | 초기 범위·기본 정렬·미확인 표시 확정. 유형별 접수일 해석 등 세부 흐름은 D-04에서 결정 |
| 모니터링·알림 | 신규·변경 공고의 주기적 탐색과 선제 알림 | 후속 |
| 여러 공고 비교 | 여러 공고·주택형의 결과를 나란히 비교하는 기능 | 후속. 개별 공고 분석과 다중 채팅 유지에는 영향 없음 |
| 호가·리치고·수익모델 | 호가 수집·표시·추정, 리치고 연동, 수익모델 설계 | 제외 |
| 확정 판단·실행 | 미래 수익 보장, 개인 청약 자격·대출 승인액·총취득비용의 근거 없는 확정, 청약 신청·거래 실행 | 현재 범위 밖 |

기초 자금표·법령 근거 탐색·출퇴근 경로 조회는 2026-11-10 사용자 결정으로 초기 범위에 포함했다. API 확보나 이 결정이 개인 자격 자동 판정, 모든 후보의 출퇴근 사전 계산, 세금·대출 승인액 자동 계산까지 포함하는 것은 아니다. 해당 기능의 입력·근거·결과 범위는 §4.3을 따른다.

## 4. 사용자 흐름을 제안한다

**조건 기반 공고 탐색 → 한 번에 한 공고·한 주택형 분석과 주변 실거래 비교**를 초기 범위로 확정했다. 여러 공고·주택형을 나란히 비교하는 기능은 후속으로 둔다. 다음 흐름을 채팅·후보 목록·보고서 화면에 배치하는 방식은 **설계 제안 P-01**이며, 상세 입력과 화면 구성은 D-04에서 결정한다.

| 단계를 진행한다 | 제품이 보여줄 결과를 정한다 | 사용자가 선택하거나 확인한다 |
| --- | --- | --- |
| 1. 로그인하고 채팅을 시작·재개한다 | 인증 후 계정의 기존 채팅 목록과 이번 분석에 적용할 확인된 조건 | 첫 탐색부터 로그인 필요. 다른 기기에서 이어 쓰거나 새 분석 시작 |
| 2. 탐색 조건을 정한다 | 필수 희망 시·군·구의 복수 선택·구매 가격 상한, 선택 공급면적 최소~최대(㎡·평 병기)·입주 시작월~종료월 | 선택 조건 없이도 탐색 가능. 예산은 사용자가 정한 상한이며 자동 대출 판정이 아님 |
| 3. 공고 후보를 찾는다 | 접수 중 마감일순→예정 시작일순의 조건 충족 공고와 별도 확인 필요 목록, 적용 조건·미확인 사유·분양가+필수 옵션 | 후보 선택·조건 수정·종료 공고 포함 선택. 세금·금융비용은 별도 표시 |
| 4. 공고를 확인한다 | 선택한 공고의 이름·식별자·주소·접수 상태·공식 출처, 공식 PDF 자동 확보 결과 | 확보 실패 시 업로드로 보완. 업로드도 같은 공고·회차와 원문 근거 확인 |
| 5. 주택형과 비교 조건을 정한다 | 자동 점검을 통과한 공급/전용면적, 확인된 호실의 분양가+필수 옵션 범위, 공급면적 기본 ±5%·거래 기간·종류 및 보류 항목 | 한 공고의 주택형 하나 선택. 특정 호실을 고르면 그 가격으로 비교하고 면적 범위 변경은 확인 후 적용 |
| 6. 비교 대상을 찾는다 | 같은 동·읍·면의 확인 후보, 정상 0개이면 구 또는 구 없는 시·군 후보, 범위·보류 사유 | §6의 기본 확대에는 추가 확인 불필요. 그 밖의 조건 변경·직접 지정은 확인 |
| 7. 결과를 읽는다 | 단지별 통계, 본체 가격·필수 옵션·납부 일정, 지역 뉴스, 기초 자금표·법령 근거·출퇴근 경로 및 누락 사유 | 원문 확인, 필요한 자금·목적지 조건 입력, 조건 변경 요청, 보고서 저장·PDF 다운로드 |
| 8. 프로필 변경을 검토한다 | 최근 대화에서 추출한 변경 항목의 이전 값·새 값·근거 | 승인·거절·취소. 승인 전 공유 프로필 유지 |
| 9. 다시 검토한다 | 변경된 조건으로 생성한 새 결과와 적용 시점 | 다른 채팅·기존 결과와 혼동하지 않도록 분석 조건 확인 |

다른 탐색 조건을 충족하는 주택형·호실 중 **분양가+필수 옵션이 예산 이하인 항목이 하나라도 확인되면 공고를 탐색 결과에 포함**하고, 해당 주택형·호실과 확인한 금액을 표시한다. 일부 항목의 충족을 공고 전체의 모든 주택형·호실에 일반화하지 않는다. 공고 최고금액이 예산을 넘는다는 이유만으로 공고 전체를 부적합 처리하지 않는다. 예산 이내 항목은 확인되지 않았지만 다른 주택형·호실 가격이 미확인이라면 예산 판정을 보류한다. 접수가 종료된 검증 사례는 현재 신청 가능한 공고처럼 제시하지 않는다.

공고 탐색의 예산 비교값은 **분양가 + 해당 주택형·호실에 적용되는 필수 옵션 금액**이다. 이 소계를 총취득비용으로 표시하지 않는다. 세금·금융비용의 확인된 값·미확인 상태와 별도 비용이라는 사실을 구분해 안내한다. 필수 옵션의 금액이나 적용 여부가 불명확하면 0원으로 채우지 않고 해당 예산 판정을 보류한다. 선택 면적·입주 시기는 §4.1의 판정 기준을 따른다.

선택한 주택형의 분양 가격은 **확인된 호실별 분양가+필수 옵션 소계의 최소~최대 범위**를 기본으로 보여준다. 특정 호실을 선택하면 그 호실의 확인된 소계로 주변 실거래와 비교한다. 일부 호실만 확인됐다면 확인한 호실의 범위임을 표시하고 미확인 항목은 별도로 남긴다. API의 주택형 최고금액을 호실 가격으로 간주하거나 범위를 임의의 최저가·평균가 하나로 대체하지 않는다. 호실별 필수 옵션 적용이 불명확한 소계는 범위 계산에서 보류한다.

### 4.1 공고 탐색의 지역·유형·상태를 적용한다

희망 지역은 **시·군·구 단위로 여러 곳을 선택**할 수 있다. 예를 들어 서울특별시 광진구와 성동구를 선택하면 두 지역의 공고를 찾는다. 같은 이름의 지역은 상위 지역과 코드로 구별한다. 이 선택은 공고를 찾는 범위이며, 개별 공고의 분석은 소재지를 기준으로 §6의 동·읍·면→구 또는 시·군 규칙을 적용한다. 여러 희망 지역의 거래를 하나의 비교 범위로 섞지 않는다.

희망 면적은 **공급면적의 최소~최대 범위**를 선택 입력하고 ㎡와 평을 함께 표시한다. 입력한 단위를 보존하고 같은 단위로 환산해 양 끝 경계를 포함하여 판정한다. 표시용 반올림으로 조건 충족 여부를 바꾸지 않으며, 전용면적만 확인된 값으로 공급면적 조건을 충족 처리하지 않는다. 이 탐색 범위는 사용자가 찾는 주택형의 크기이며, 공고를 선택한 뒤 적용하는 주변 실거래의 기본 ±5%와 별개다.

희망 입주 시기는 **시작월~종료월**을 선택 입력한다. 해당 월 범위와 공식 입주 예정 기간이 겹치는 공고를 포함하며 경계월도 포함한다. 공식 자료가 예정월만 제공하면 그 월 단위로 비교하고 특정 입주일로 바꾸지 않는다. 입주 예정 시점을 확인하지 못하거나 출처가 충돌하면 조건 충족으로 추정하지 않고 판정을 보류한다.

면적·입주 시기를 입력하지 않으면 해당 선택 조건으로 공고를 제한하지 않는다. 입력 범위가 역전되거나 단위가 불명확하면 확인을 요청한다. 입력한 면적·예산·입주 조건은 같은 주택형·호실의 적용 근거에 연결하며, 서로 다른 주택형이 각각 한 조건만 충족한 것을 합쳐 공고 전체가 조건에 맞는다고 표시하지 않는다.

초기 지원 공고는 **아파트 신규분양·무순위·잔여세대·재공급**이다. API의 조회 유형·필드 및 공식 공고의 표시 유형을 대조하며, 같은 공고를 여러 유형에서 받았다는 이유로 중복 공고로 제시하지 않는다. 유형별 필드·PDF 서식 검증은 지원 범위 결정과 별개로 수행한다. 이 범위를 임대주택·오피스텔 등으로 자동 확대하지 않는다.

기본 목록에는 **접수 중·접수 예정 공고**를 표시한다. 종료 공고는 사용자가 포함을 선택했을 때만 목록에 넣고 종료 상태를 명확히 표시한다. 유형별 접수일이나 시각을 확인하지 못하면 상태를 추측하지 않고 미확인으로 남긴다. 공고의 접수 상태와 개인의 청약 자격·신청 가능 여부는 구분한다.

조건 충족 목록은 **접수 중 공고를 먼저 마감일이 빠른 순으로, 접수 예정 공고는 시작일이 빠른 순으로** 보여준다. 적용한 접수 상태·날짜와 기준시점을 표시한다. 이 정렬은 공고 탐색 목록에만 적용하며 주변 실거래 단지의 공급면적·거리 순서를 바꾸지 않는다. 종료 공고·날짜 미확인·동률의 세부 배치는 D-04에서 정한다.

입력한 조건의 충족 여부가 미확인인 공고는 **조건 충족 목록과 분리한 ‘확인 필요’ 목록을 기본으로 함께 제공**하고, 가격·필수 옵션·공급면적·입주 시기 등 어떤 항목을 확인하지 못했는지 표시한다. 조건 충족 공고의 건수에 합산하거나 충족 표시를 붙이지 않는다. 입력하지 않은 선택 조건의 자료가 없다는 이유만으로 확인 필요 목록에 넣지 않는다.

같은 공고에 모든 적용 조건을 충족하는 주택형·호실이 하나라도 확인되면 충족 목록에 포함하고, 다른 주택형·호실의 미확인은 그 공고 안에 표시한다. 공고를 두 목록에 중복 집계하지 않는다. 확인된 조건 위반으로 부적합이 확정된 공고와 아직 판정할 수 없는 공고도 구분한다. 확인 필요 공고나 조회 실패가 남아 있으면 충족 목록이 비었다는 이유만으로 ‘조건에 맞는 공고가 전혀 없음’을 확정하지 않는다.

### 4.2 공식 PDF를 확보하고 핵심 값을 점검한다

선택한 공고의 **공식 PDF 자동 확보를 기본으로 하며, 실패하면 사용자 업로드로 보완**한다. 확보 실패 사유와 보완 경로를 보여주고, PDF가 없어도 독립적으로 확인된 API 기본 정보는 제공한다. 상세 가격·면적 등 PDF 근거가 필요한 값은 확보·점검 전까지 미확인으로 남긴다. 업로드한 문서도 공고 식별자·회차·출처를 확인하며, 파일을 업로드했다는 사실을 공식성이나 값의 정확성 확인으로 취급하지 않는다.

분양가·필수 옵션·공급면적 등 핵심 값은 **원문 대조·일관성 자동 점검을 통과하면 분석에 사용**한다. 매번 운영자 또는 사용자가 값을 승인해야 하는 절차는 두지 않는다. 공고·주택형·호실의 연결, 원문 페이지의 값·단위·항목명, 필수 옵션의 적용 대상, 공급/전용면적 구분과 합계의 일관성을 확인한다. 값별로 원문 출처·페이지와 점검 상태를 보존하고 표시한다. 표 추출 성공이나 모델의 자체 확신만으로 점검 통과를 대신하지 않는다.

원문 대조 실패·가격/면적 충돌·적용 대상 불명확·다른 회차는 해당 값을 보류하고 이유를 표시한다. 보류한 값을 0원 또는 유사한 값으로 채우거나 예산 판정·공급면적 비교에 사용하지 않는다. 다른 값이 독립적으로 점검을 통과했다면 그 값에 근거한 결과는 제공한다. 정정본·참조 문서의 적용 관계가 불명확한 값도 보류하며, 정정본 선택과 서식별 점검의 구체 기준은 D-04에서 관리한다.

자동 점검을 제품 방식으로 채택한 것과 그 정확도를 검증한 것은 별개다. 스캔·복잡한 표·주택형별 옵션·정정 공고를 포함한 검수 자료로 자동 점검을 평가해야 하며, E-02의 한 공고에 대한 과거 수동 검수를 전체 자동화의 검증으로 확대하지 않는다.

### 4.3 초기 보조 기능의 입력과 결과를 구분한다

**기초 자금표·법령 근거 탐색·출퇴근 경로 조회를 모두 초기 서비스에 포함**한다. 자금표와 경로에 필요한 입력은 해당 기능을 사용하기 위한 조건으로 구분하며, 공고 탐색의 필수 조건인 희망 지역·예산에 자동으로 추가하지 않는다. 필요한 입력이나 근거가 없으면 해당 결과의 상태와 보완 항목을 표시하고, 독립적으로 제공 가능한 공고·비교 결과는 유지한다.

| 기능을 제공한다 | 입력과 근거를 확인한다 | 결과의 의미를 구분한다 |
| --- | --- | --- |
| 기초 자금표 | 현재 보유 자금과 날짜별 추가 자금의 금액·확정/예상 상태, 공고의 계약금·중도금·잔금·필수 옵션 납부 근거 | 시점별 납부액·누적 자금·부족분을 보여주고 예상 자금 반영은 가정으로 구분한다. 상세 자금은 분석별 저장. 탐색 예산을 현금으로 사용하거나 대출 승인액·세금을 자동 확정하지 않음 |
| 법령 근거 탐색 | 공고 조건, 관련 법령 원문과 적용 기준시점·시행 버전·출처 | 관련 근거와 추가 확인할 조항·예외를 제시한다. 공고 시점의 조건에 현행 법령을 그대로 대입하지 않으며 미확인 경과규정이나 예외를 확정 해석하지 않음 |
| 출퇴근 경로 조회 | 선택한 공고 단지·사용자 지정 목적지와 대중교통/연결 도보·자동차의 요청 조건·조회 시점 | 두 교통수단 범위를 초기 지원하고 조회한 수단·출처·시간 조건을 구분한다. 미제공 값·오류·조회 불가를 정상 0분이나 경로 없음과 구분 |

자금표에는 **현재 보유 자금과 날짜별 추가 자금**을 입력받고, 사용자가 지정한 **확정·예상 상태**를 구분해 시점별 납부액과 부족분을 보여준다. 사용자 입력의 확정 표시는 금융기관이 검증한 금액이나 대출 승인 결과를 뜻하지 않는다. 예상 자금을 반영한 계산에는 해당 가정과 금액·날짜를 표시하며, 확정 자금만으로 충당한 것처럼 표현하지 않는다.

납부 시점까지 들어오는 것으로 입력된 자금과 그때까지의 누적 납부액을 대조한다. 납부일 뒤의 추가 자금으로 이전 납부일의 부족분을 없애거나 같은 보유 자금을 납부 회차마다 새 자금처럼 중복 계산하지 않는다. 금액·유입일·납부 근거가 미확인인 항목은 표시하고 그 값에 의존하는 부족분 계산을 확정하지 않는다. 공유 프로필의 구매 가격 상한과 분석별 보유·추가 자금을 구분한다.

출퇴근 조회는 **대중교통·연결 도보와 자동차 경로를 모두 초기 지원**한다. 교통수단별 요청 조건·조회 시점·출처·결과 상태를 구분하고, 한 수단의 실패를 다른 수단의 값으로 채우지 않는다. 기존 ODsay 경로 검증을 자동차 경로 검증으로 확대하지 않는다. 자동차 경로의 데이터 출처·연동·시간 조건·이용 조건은 추가 확보·검증 과제다.

세 기능의 초기 포함과 상세 화면은 구분한다. 자금의 같은 날 유입·납부 순서와 가정별 결과 표현, 경로의 시간 조건·선택 UI, 법령 기준시점과 예외 확인 절차는 D-04·D-06·D-07에서 설계·검증한다. 출퇴근 목적지는 §4.4에 따라 확인 후 공유 프로필에 저장한다. E-05의 제한된 API 응답 확인을 개인 자금·자격·출퇴근 결과의 검증으로 확대하지 않는다.

### 4.4 계정에서 이어 쓰고 보고서를 보관한다

**첫 사용부터 로그인한 뒤 공고 탐색·분석을 시작**한다. 비로그인 상태에서는 탐색·분석을 실행하지 않고 로그인으로 안내한다. 여러 채팅과 확인한 공유 프로필, 분석 결과를 계정에 저장하고 다른 기기에서도 이어서 사용한다. 같은 계정의 채팅 목록·대화·프로필 승인 상태·분석 참조를 복원하고, 다른 계정의 자료와 분리한다. 기기를 바꾸거나 채팅을 다시 열었다는 이유로 미승인 프로필 변경안을 적용하지 않는다. 인증 수단·삭제 처리·동시 변경은 D-06에서 구체화한다.

공유 프로필에는 **탐색 조건(희망 지역·구매 가격 상한·공급면적 범위·입주 시기)과 출퇴근 목적지**를 저장한다. 대화에서 변경안을 만들면 이전 값·새 값·근거를 보여주고 사용자가 확인한 항목만 반영한다. **현재 보유 자금·추가 자금의 금액/날짜·확정/예상 상태 등 상세 자금은 해당 분석에 저장**한다. 다른 분석에 자동 적용하거나 공유 프로필의 예산 값으로 변환하지 않는다. 분석별 자금도 계정 내 해당 분석을 다시 열면 복원하며, 같은 계정에 저장됐다는 이유로 여러 채팅의 공유 값으로 취급하지 않는다.

분석 보고서는 **서비스 안에서 저장·다시 열기와 PDF 다운로드**를 초기 제공한다. 저장한 보고서와 해당 PDF는 같은 공고·주택형·호실 선택, 적용 조건·조회 시점·출처·미확인 사항을 보존한다. 다른 기기에서 다시 열 때도 그 결과의 조건과 값을 복원한다. 새로 조회한 결과나 새 프로필을 기존 보고서에 조용히 덮어쓰지 않으며, 갱신 결과는 적용 시점을 구분한다. PDF의 표 배치·분량 등 상세 구성은 D-04에서 설계한다.

사용자가 입력한 **대화·프로필·분석별 자금은 사용자가 삭제할 때까지 보관**한다. 개별 자료 삭제와 계정 삭제를 지원하며, 삭제 범위·관련 자료에 미치는 영향과 처리 상태를 확인할 수 있게 한다. 삭제가 반영된 사용자 입력이 다른 기기에서 다시 복원되거나 새로운 분석의 기본값으로 재사용되지 않아야 한다. 연관 보고서·백업·참조 관계의 처리와 완료 기준은 D-06에서 구체화한다. 외부 API 원문·공고 PDF·뉴스·경로 자료의 보관 기간과 재사용 권한은 이 정책으로 정하지 않으며 소스별 조건을 따로 확인한다.

| P-05 | LLM은 공고 구조화·근거 있는 설명을 보조하고 코드가 단위·지역·금액·통계를 처리 | 모델·호스팅·정확도/비용/응답시간 목표와 자동 점검 구현. 점검 통과 값을 사용하는 제품 방식은 R-03으로 확정 |
| P-06 | 적용 시·군·구의 실거래를 수집한 뒤 검증된 코드로 동·읍·면을 구분해 우선 지역의 결과를 제공 | 저장·캐시·수집 주기·코드 매핑·미포함 자료 보완 방식. API 요청 범위가 커도 사용자 결과 범위를 자동 확대하지 않음 |

## 6. 지역 검색과 비교 규칙을 정의한다

**우선 지역**은 공고가 속한 같은 동·읍·면이다. 동은 법정동을 기준으로 하며, 읍·면은 검증된 소속 코드와 경계로 묶는다. 하위 주소가 리로 제공되면 소속 읍·면을 확인한다. **확대 지역**은 구가 있는 곳의 같은 구이며, 구가 없으면 같은 시·군이다. 소속·구 존재 여부를 확인하지 못하면 이름이나 좌표로 추측하지 않고 지역 판정을 보류한다. 아래 규칙은 동→구 사례와 읍·면·구 없는 시·군에 공통으로 적용한다.

### 6.1 비교 가능성과 정상 0개를 구분한다

‘매물’은 이 제품에서 비교할 아파트 단지를 뜻한다. 호가 매물 수가 아니라 **선택한 거래 종류·기간·면적 조건을 충족하는, 해제를 제외한 유효 거래가 1건 이상 있고 단지 식별과 공급면적 대응이 확인된 후보**를 판단한다. §6.3에서 선정한 면적에 어느 거래 종류든 유효 거래가 1건 이상 있으면 주변 후보 수에 포함한다. 1~2건이라는 이유로 후보에서 제외하거나 우선 지역을 정상 0개로 처리하지 않는다.

각 단지의 해당 면적·기간·거래 종류별 건수를 표시하고, 1~2건에는 적은 표본이라는 안내를 붙인다. 1건이면 중위값·최소값·최대값은 같은 거래금액이다. 거래 건수를 늘리기 위해 기간·면적·지역을 자동 변경하지 않는다. 건수 조건을 충족하더라도 면적 미확인·연결 충돌·해제 여부 미확인 등 다른 보류 사유가 해소된 것으로 취급하지 않는다.

면적 대응 자료가 없는 후보는 ‘면적 불일치’가 아닌 ‘미확인’이다. 다른 회차 PDF, 주소 충돌, 단지 연결 보류, 부분 수집, 인증/통신/업무 오류도 정상 0개와 구분한다. K-apt 목록 97/97개 확보는 해당 API 목록의 완전성이지 동 안의 모든 비교 가능 단지가 없다는 증거가 아니다.

**정상 0개**는 요청한 지역·기간·거래 종류에 필요한 조회와 판별이 끝나고, 후보의 존재 여부를 바꿀 미확인 사항 없이 비교 대상이 0개인 상태다. ‘0개로 확인됨’과 ‘확인된 후보가 아직 0개임’을 구분한다. 우선 지역의 정상 0개가 증명되지 않으면 자동 확대를 실행하지 않는다.

| 판정을 진행한다 | 필요한 근거와 상태를 남긴다 |
| --- | --- |
| 1. 분석 범위를 고정한다 | 공고·주택형·지역 계층·거래 종류·계약일·면적 조건·조회 시점과 규칙 버전 |
| 2. 필요한 수집을 확인한다 | 해당 요청의 월·페이지·전체 건수·업무 응답을 확인. 한 요청의 0건, 정규화 성공, K-apt 목록 완료를 전체 비교 후보 0개로 대체하지 않음 |
| 3. 후보에서 제외할 근거를 구분한다 | 확인된 기간 밖·해제·대상 종류 밖·지역 밖·자체 단지·공급면적 범위 밖 등은 적용 규칙과 원문 근거를 기록. 단순 결측·연결 실패를 불일치 증명으로 쓰지 않음 |
| 4. 비교 가능 또는 보류로 나눈다 | 포함 후보에는 거래 유효성·지역 배정·단지 식별·공급면적 대응의 확인을 요구. 각 단계의 미확인·충돌은 별도 기록하며 사전 자격 플래그만으로 최종 승인하지 않음 |
| 5. 지역 결론을 낸다 | 확인된 후보가 있으면 현재 범위에서 제공. 0개이면 수집 완료와 결론을 바꿀 보류의 부재를 확인한 뒤에만 정상 0개. 그 외에는 보류 |

거래가 확인된 기간 밖이거나 해제된 것으로 확인돼 이미 제외되는 경우에는 다른 필드가 비었다는 이유만으로 비교 후보로 되돌리지 않는다. 반대로 지역 미배정 행이 우선 지역에 속할 가능성을 배제할 근거가 없으면 그 지역의 정상 0개 판정은 보류한다. 공급면적 대응이 없는 거래를 전용면적 수치만으로 공급면적 범위 밖이라고 추정하는 규칙은 채택하지 않는다.

이 판정의 모집단은 표시한 수집 시점·요청 범위에서 제공된 거래다. 해당 지역의 모든 주택 재고를 조사했거나 향후 지연 신고까지 없다는 뜻은 아니다. 실제 필수 식별 경로와 보강 정보의 구분은 D-01·D-02의 근거 표로 검증하며, 이 절차를 이유로 주소 충돌을 무시하거나 기존 확인 조건을 낮추지 않는다.

### 6.2 결과 범위와 동작을 정한다

아래 후보 수는 **분석에 포함된 거래 종류를 합친 고유 주변 단지 수**다. 대상 단지 자체 거래는 제외한다. 거래 종류별로 서로 다른 지역 범위를 적용하지 않는다.

| 관찰한 상태를 확인한다 | 적용할 범위를 정한다 | 결과와 다음 행동을 정한다 |
| --- | --- | --- |
| 우선·확대 지역 식별 불가 | 미확인 | 주소·소속을 확인한다. 이름 추측이나 좌표 반경으로 대체하지 않음 |
| 우선 지역에 확인된 후보 1~5개 | 같은 동·읍·면 | 해당 후보만 제시. 확대 지역에서 수를 채우지 않음 |
| 우선 지역에 확인된 후보 5개 초과 | 같은 동·읍·면 | 면적 차이순·직선거리순으로 최대 5개 선정. 범위 보충 없음 |
| 우선 지역에 확인된 후보와 미확인 후보가 함께 있음 | 같은 동·읍·면 | 확인된 결과와 미확인 수·사유 제공. 완전한 목록·순위로 표시하지 않음 |
| 우선 지역의 확인된 후보 0개, 미확인 또는 미완료 조회 있음 | 우선 지역 판정 보류 | 확대하지 않고 누락·실패와 필요한 보완을 표시 |
| 우선 지역이 정상 0개 | 같은 구 또는 구 없는 시·군 | 추가 승인 없이 확대하고 실제 지역·이유 표시 |
| 확대 지역에서 후보 확인 | 같은 구 또는 시·군 | 같은 선정 순서로 최대 5개와 범위·조건 표시. 미확인도 고지 |
| 확대 지역도 정상 0개 | 그 범위에서 종료 | 비교 자료 부족 안내. 인접 시·군·구·기간·면적 자동 확대 없음 |
| 확대 지역 조회 실패·판정 미완료 | 확대 지역 판정 보류 | ‘이 지역에도 없음’으로 표시하지 않음 |

지역 판정은 출처별 실응답에서 확인한 `sggCd`·`umdCd` 또는 공식 주소·지역코드의 검증된 대응을 사용한다. 모든 거래 API에 같은 식별 필드가 있다고 가정하지 않는다. 행정동명·동일 이름·좌표 거리로 소속 지역을 대체하지 않는다. 권리 거래의 식별 필드, 리→읍·면과 상위 시·군·구 매핑은 별도 자료 검증 대상이다.

사용자 표시 문구의 예시는 다음과 같다.

- ‘구의동에서 비교 가능한 단지 2개를 확인했습니다.’
- ‘구의동 내 비교 가능한 단지가 없어 광진구로 확대했습니다.’
- ‘구의동의 일부 후보는 공식 공급면적 대응 자료가 없어 비교를 보류했습니다. 대응 근거를 확보해야 합니다.’
- ‘현재 기간·면적 조건에서 광진구의 비교 자료를 찾지 못했습니다.’ — 구의 정상 0개일 때만 사용.

직접 지정은 **기본 지역 규칙으로 이미 정해진 현재 범위 안에서, 전체 고유 주변 최대 5단지 안의 교체**로 지원한다. 지정 단지도 같은 면적·기간·유효 거래·식별과 근거 확인 기준을 적용한다. 자동 선정과 직접 지정을 합쳐 한도를 세며, 이미 5개이면 사용자가 교체 대상을 정한 뒤 반영한다. 범위 밖 단지나 기준 미충족·미확인 단지는 사유를 표시하고 확정 비교표에 넣지 않는다. 직접 지정으로 지역 판정을 바꾸거나 우선 지역의 후보를 확대 지역에서 자동 보충하지 않는다.

### 6.3 후보를 선정하고 대상 단지 자체 거래를 구분한다

기본 비교 범위는 **선택한 주택형의 공급면적 ±5% 이내**다. 선택 공급면적을 S, 후보 거래에 대응된 공급면적을 C라 할 때 두 면적이 확인되고 0보다 큰 경우 **0.95×S ≤ C ≤ 1.05×S**를 적용한다. 예를 들어 100㎡이면 95~105㎡이며 경계값을 포함한다. 표시용 반올림으로 범위 안팎을 바꾸지 않는다. 적용 범위를 결과에 표시하며 변경은 R-14에 따라 사용자가 확인한 경우에만 해당 분석에 적용한다.

면적 대응이 확인돼 범위를 벗어난 후보와 공급면적 자체가 미확인인 후보를 구분한다. 후자는 범위 밖으로 간주하지 않으며 정상 0개를 확정하는 근거로 쓰지 않는다. ±5%는 사용자와 합의한 제품 설정이며 실제 후보의 비교 적합성·연결 가능률을 검증한 수치는 아니다.

단지별로 분석 기간·거래 종류에 유효 거래가 1건 이상 있고 공급면적 대응이 확인된 면적 중, 허용 범위 안에서 **선택 주택형과 공급면적 차이가 가장 작은 면적**을 선정한다. 이 면적으로 단지 순위를 정하며 **그 면적의 거래만** 가격 통계에 사용한다. 더 많은 거래가 있다는 이유로 덜 가까운 면적을 고르거나 허용 범위 안의 다른 면적 거래를 합치지 않는다. 선정한 면적과 선택 주택형의 면적 차이를 표시하고, 해당 면적의 가격·건수를 거래 종류별로 나눈다.

단지 간 순서는 **공급면적 차이가 작은 순 → 차이가 같으면 공고 단지와 직선거리가 가까운 순**이다. 단지 식별과 일치하는 확인된 좌표 사이의 직선거리를 사용하고 결과에 거리 종류를 표시한다. 도보·자동차 경로 거리나 출퇴근 시간으로 대체하지 않는다. 더 가까운 단지를 면적이 더 비슷한 단지보다 먼저 고르지 않으며 거리순을 지역 확대나 반경 제한의 근거로 쓰지 않는다.

서로 다른 두 면적의 차이가 같은 경우, 단지 대표 좌표의 선택·충돌, 단지 간 완전 동률과 거리 미확인 처리는 D-03에서 구체화한다. 미확인 거리를 0으로 채워 우선 선정하거나 면적 선택의 동률을 정상 0개로 처리하지 않는다. 서로 다른 면적도 조용히 합산하지 않는다.

대상 단지 자체 거래는 **주변 비교표와 구분한 별도 참고**로 표시한다. 확인된 자체 거래는 우선·확대 지역의 주변 후보 집합과 5단지 집계에서 제외한다. 우선 지역의 주변 후보가 정상 0개이면 자체 거래가 있어도 같은 구 또는 구 없는 시·군으로 확대한다. 다른 후보의 면적 미확인·주소 충돌·부분 수집·오류는 기존 보류 규칙을 적용한다.

자체 거래도 해제 여부와 거래 종류·기간·면적 기준 및 출처를 구분한다. 공급면적 대응이 미확인인 값을 동일 면적의 비교값으로 사용하지 않고 보류 사유를 표시한다. 같은 이름이나 같은 지번이라는 이유만으로 대상 단지로 판정하지 않는다.

### 6.4 거래 종류를 공통 범위에서 비교한다

분석에 포함된 매매·분양권·입주권 중 하나라도 우선 지역에 확인된 주변 단지가 있으면 전체 보고서를 같은 동·읍·면 범위로 유지한다. 다른 종류만 확대 지역에서 보충하지 않는다. 종류별 실제 판정에 따라 '현재 지역·기간·면적 조건의 비교 자료 없음', '확인 보류', '조회 실패'를 구분한다.

분석에 포함된 모든 종류의 필요한 조회·판별이 완료돼 주변 후보 전체가 정상 0개일 때만 같은 구 또는 구 없는 시·군으로 확대한다. 어느 종류에 결론을 바꿀 미확인이나 실패가 남으면 정상 0개로 바꾸지 않는다. 확대 후에도 공통 범위와 종류별 통계 분리를 유지한다.

단지 식별 근거로 같은 단지임을 확인한 경우 매매와 권리 거래가 함께 있어도 고유 단지 수는 1개다. 후보 종류를 합친 집합에서 §6.3의 순서로 최대 5단지를 선정한 뒤 각 단지의 선정 면적에 해당하는 거래를 종류별로 나눈다. 선정된 5단지 또는 선정 면적에 특정 종류의 거래가 표시되지 않는 것만으로 조회 범위 전체의 해당 종류가 정상 0개였다고 판단하지 않는다. 그 종류만 다른 면적이나 구 범위에서 자동 보충하지 않는다.

### 6.5 기본 기간과 조회 시점을 표시한다

기본 계약일 범위는 **조회일까지 최근 1년**이며 시작일과 종료일을 결과에 표시한다. 합의한 예시는 조회일이 2026-11-10이면 **2025-11-11~2026-11-10 양 끝 날짜 포함**이다. 진행 중인 2026-11월도 포함하고, 과거 수집 도구의 완료된 12개월 기본값으로 대체하지 않는다. 윤일과 시간대 경계의 세부 규칙은 D-02에서 정한다.

월 단위 API에서는 적용 계약일 범위에 걸친 월의 필요한 페이지를 수집하고, 통계·후보 판정에는 정확한 계약일 범위 안의 거래만 사용한다. 위 예시는 2025-11부터 2026-11까지 13개 계약월에 걸치지만 비교 기간 자체가 13개월인 것은 아니다. 시작 월 앞부분이나 조회일 뒤 날짜의 거래를 포함하지 않는다.

수집 완료와 정상 0개 판정은 **표시한 조회·수집 시점에 제공된 자료**에 대한 판정이다. 신고 지연·추가 신고·정정·해제로 결과가 달라질 수 있음을 표시한다. 이 설명으로 페이지 누락·통신 오류·미확인 연결을 정상 0개로 처리하지 않는다. 재조회할 때는 새 수집 시점과 변경된 결과를 구분한다.

## 8. 데이터·계산·실패 처리의 계약을 제안한다

데이터 보존 원칙은 기존 검증에서 이어받고, 아래 객체 구분과 필드 구성은 구현을 위한 설계 제안이다. 저장소나 프레임워크를 확정하지 않는다.

| 객체를 구분한다 | 보존할 내용을 정한다 | 잘못된 결합을 차단한다 |
| --- | --- | --- |
| 공고·주택형 | 공고/주택관리/모델 식별자, 유형·접수 상태, 면적 종류, 가격의 적용 대상, 원문·PDF 페이지, 문서 확보 경로·버전과 값별 자동 점검 상태 | 배열 순서·단지명만으로 병합하지 않음. API 최고금액을 개별 호실 가격으로 일반화하지 않으며 점검 전 추출값을 확정값으로 사용하지 않음 |
| 분석 조건 | 공고·주택형·거래 종류·기간·면적 기준·실제 적용 지역과 소속 코드(동·읍·면/구·시·군)·확대 사유·후보 선정 규칙 버전 | 다른 지역·기간·주택형 통계를 같은 비교값처럼 섞지 않음 |
| 거래 스냅샷 | 원문, 요청 지역/월/페이지, 수집 시각·해시, 전체 건수·완료 상태, 단위·계약일·해제/정정 상태 | 만원→원 변환 근거 보존. 이름·날짜·층·가격이 같다고 동일 거래로 제거하지 않음 |

출처 값과 계산값을 구분하고 계산식·입력 참조를 보존한다. 공급면적 대응이 검증되지 않으면 전용면적 시험 통계를 공급면적 기준 비교표에 넣지 않는다. 가격 차이는 어떤 본체 가격/옵션 소계와 어떤 단지 통계를 비교했는지 표시해야 하며 확정 수익으로 표현하지 않는다. 가격 차이의 계산식·비율 표시 방식은 D-03에서 구체화한다.

| 데이터 상태를 구분한다 | 화면에서 전달할 의미를 정한다 | 계산·검색에서 처리한다 |
| --- | --- | --- |
| 확인됨 | 출처와 적용 조건을 확인한 값 | 비교 입력 조건 충족 시만 사용 |
| 정상 0건 | 필요한 조회·판별을 완료했으나 대상 없음 | 우선 지역이면 구 또는 구 없는 시·군 확대. 확대 지역이면 자료 부족 |
| 일부 수집 | 페이지 누락·전체 건수 변경 등 | 전체 통계·후보 순위 확정 및 0개 판정 보류 |
| 미제공·미확인 | 필드 없음·빈 값·대응 근거 없음 | 0원·0분·조건 불충족으로 대체하지 않음 |
| 조회 실패 | 인증·네트워크·업무 오류 | 재시도/보완 가능성과 독립적으로 확인한 결과 제공 |
| 연결 보류·출처 충돌 | 여러 후보·주소 차이·다른 집계 값 | 양쪽 근거 보존, 대표값 임의 선택 금지 |

실제로 K-apt는 HTTP 200 안에 API 오류 04가 있었고, ODsay는 근거리 요청 오류 -98과 `totalWalkTime=-1`을 반환했다. 각각 조회 성공·0분 경로로 취급하지 않는다. ODsay -1은 도보시간 미제공으로 보존한다.

대화·화면·PDF는 같은 구조화된 결과의 공고·주택형·면적·지역·기간·거래 종류·수치·건수·보류 상태를 사용한다. 설명 과정에서 확인된 후보 수를 전체 후보 수로 바꾸거나 추출·계산에 없는 수치를 추가하지 않는다. 보류에는 재시도 가능 여부, 사용자 입력 필요, 공식 자료 확보 필요 등 실제로 수행할 수 있는 다음 행동을 표시한다. 진행 중인 작업이 없는데도 ‘판단 중’으로만 표시하지 않는다.

## 9. 운영과 검수의 조건을 정한다

- API 키는 서버 측 비밀정보로 관리하고 클라이언트·보고서·일반 로그·공유 산출물에 포함하지 않는다. 사용자 비밀번호·OTP를 대화로 받지 않는다. 인증값과 계정별 운영 기록은 로컬에서 관리하며 이 저장소에 포함하지 않는다.
- 공고 PDF는 자동 확보 후 실패 시 업로드로 보완하며 두 경로에 같은 식별·자동 점검 기준을 적용한다. 자동 추출값·자동 점검 통과값·별도 수동 검수값을 구분한다. 원문 회차·페이지 확인에 실패하면 해당 항목을 보류하며, 다른 항목의 검증된 결과는 제공한다. 스캔·복잡한 표·정정 공고의 자동 점검은 추가 검증한다.
- ODsay는 현재 등록된 서버 환경의 소량 호출 성공만 확인했다. 배포 IP, 대량 사전 계산, 결과 저장·재사용 허용 범위는 운영 전 확인한다. 로컬 진단 증거의 장기 보관 허용도 미확인이다. [ODsay 이용약관 4.5.10](https://lab.odsay.com/doc/totalPolicy)
- NAVER 뉴스의 계정 상세 과금·운영 한도, 본문 수집·LLM 입력·표시·보관 범위는 별도 확인한다. OpenAI는 키 설정 존재만 확인했고 모델 인증·정확도·성능·비용을 검증하지 않았다.
- 사용자 입력은 삭제까지 보관하는 정책을 따르되 삭제·접근 통제의 구현은 별도 검증한다. API·공고 PDF·K-apt·카카오 주소/좌표·법령·뉴스·교통 자료는 소스별 저장·가공·LLM 입력·표시·PDF 내보내기 조건을 확인한다. 사용자 입력의 보관 정책을 제3자 자료의 무기한 보관 허용으로 해석하지 않는다.
- 보고서 복원·PDF 요구와 소스별 조건이 함께 성립하도록 저장 가능한 값·근거·링크·재조회 항목의 계약을 정한다. 필요한 허용 범위를 확보하지 못하면 해당 요구의 출시 준비가 끝난 것으로 표시하지 않는다. 성능·비용 상한은 D-07에서 정하며 목표 수치를 임의로 선언하지 않는다.

| A-56 | 사용자가 입력한 대화·프로필·분석별 자금의 개별 자료 또는 계정 삭제를 요청함 | 삭제 전까지 보관하고 삭제 범위·관련 영향·처리 상태를 표시. 삭제 반영 뒤 다른 기기나 새 분석에서 해당 입력을 복원·재사용하지 않음. 계정 삭제도 지원하며 제3자 자료 보관 조건을 사용자 입력 정책으로 대체하지 않음 | R-12·R-13. 연관 자료·백업 처리 D-06 구체화 후 검증 |

R-16~R-18은 초기 기능이며 A-36~A-38을 포함한 검수가 필요하다. API 데이터 검증을 개인 법률·금융 판단이나 실제 출퇴근의 검증으로 확장하지 않는다.

사용자 가치 측정은 D-05의 후속 과제다. 근거를 갖춘 비교 완료 비율, 전체 검토 후보 중 공급면적까지 연결된 비율, 원문 근거가 연결된 표시값 비율, 사용자 수동 보완 부담을 측정 후보로 제안한다. 각 분모·제외 조건·수집 방법·목표치를 합의하기 전에는 성공 KPI로 확정하지 않는다.

사용자 선택을 반영한 요구 기준본이며 아래 항목을 수행한 기록은 아니다. P와 D의 구현 세부를 확정 요구로 바꾸지 않고, 각 기능 구현 전에 관련 설계·자료 검증 결과를 남긴다.

현재 가장 큰 공백은 공급면적 대응 자료다. 이 자료가 없으면 주소가 연결된 후보도 최종 비교 가능으로 확정할 수 없다. 권리 식별·읍면/시군 코드·PDF 자동 점검·자동차 경로·소스별 이용 조건은 실제 검증이 남아 있다. 미확인 값을 채우거나 사용자 요구를 조용히 줄여 이 공백을 감추지 않는다.

**개발 시작점:** 기존 조회 도구의 확인된 결함을 먼저 수정하고, 공급면적·권리·지역의 근거 표와 대표 공고의 수작업 결과를 만든다. 이를 데이터 계약·화면 명세·D-05 사용자 검토에 연결하며, 확정한 제품 정책은 유지한다.
