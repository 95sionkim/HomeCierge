# 선택한 호실의 납부 일정과 자금표

자금표는 한 분석에 저장한 자금과 선택한 호실의 분양대금·필수 옵션 납부 일정을 대조한다. 로그인한 사용자가 자금을 수정한 뒤 다시 조회하면 같은 수집본의 일정으로 부족액을 다시 계산한다. 공고 탐색에 입력한 예산과 상세 자금은 각각 입력한다. [PRD §5.3](../prd/01-product-prd.md#53-초기-보조-기능의-입력과-결과를-구분한다)

## 화면에서 자금을 입력하고 조회한다

1. 사용자 세션으로 자기 분석의 `funding_entries`에 자금을 저장한다. `current`는 `available_on`을 기준으로 사용자가 보유한 잔액 한 건이다. 이후 마련할 자금은 `additional`로 금액·유입일을 입력한다. `certainty`는 사용자가 지정한 `confirmed` 또는 `expected`다. 각 입력은 해당 분석을 다시 열 때 복원된다.
2. `POST /api/v1/analyses/{analysisId}/funding-plan`에 사용자 Bearer 토큰, `Content-Type: application/json`과 아래 본문을 보낸다. `snapshotId`는 자기 분석에 저장된 공고 수집본의 UUID다. 주택형 번호는 앞의 0을 유지하고 호실은 수집본의 표기를 사용한다.
3. 응답 `funding-plan/v1`에서 날짜별 납부액, 이미 반영한 자금, 부족액과 미확인 항목을 읽는다. 예상 자금이 들어오는 경우는 별도 가정으로 표시한다. 자금만 바꿀 때는 같은 요청으로 다시 계산한다.

```json
{
  "snapshotId": "a1100000-0000-4000-8000-000000000002",
  "modelNo": "01",
  "room": "101동 101호"
}
```

위 요청은 합성 예시다. API는 원 단위 정수를 십진 문자열로 반환한다. 큰 금액을 입력할 때는 JavaScript `Number`로 변환하는 과정에서 원 단위가 달라지지 않도록 주의한다. Supabase Data API에 쓰는 `amount_won`에는 십진 문자열을 전달할 수 있다. 사용자 프로필에는 상세 자금을 넣지 않는다. [화면팀 인계](../frontend-handoff.md)

| 응답에서 읽는다 | 사용자에게 표시한다 |
| --- | --- |
| `selection`, `dataOrigin`, `scheduleStatus` | 분석·수집본·주택형·호실, 합성 또는 실수집 여부, 해당 일정의 이용 가능 상태 |
| `userInputs.funds`, `assumptions` | 입력한 보유·추가 자금, 날짜·확정/예상 구분, 계산에 반영한 가정 |
| `rows[].knownDueWon`, `knownCumulativeDueWon` | 해당 날짜에 확인한 납부액과 지금까지 날짜가 확인된 누적 납부액 |
| `rows[].scenarios.confirmedOnly`, `includingExpected` | 확정 자금만 사용한 경우와 예상 유입까지 포함한 경우의 가용 자금과 부족액(`shortfallWon`). 계산에 필요한 값이 없으면 `null`과 보류 사유 |
| `components`, `undatedInstallments`, `evidence` | 분양대금·필수 옵션의 확인 상태, 금액은 알지만 날짜를 모르는 납부, 근거 문서의 판본과 페이지 |
| `requiredTotalWon`, `subtotalHoldReasons` | 같은 문서 판본에서 두 항목을 함께 확인한 호실 총액. 서로 다른 판본에만 근거가 있거나 소계가 금액 한도를 넘으면 항목별 금액과 일정만 표시 |

각 시점의 `fundsWon`은 기준 잔액에 그 시점까지 쓸 수 있는 유입액을 더한 누계다. `shortfallWon`은 같은 기간의 누적 납부액에서 이 자금을 뺀 뒤, 자금이 충분하면 `"0"`으로 표시한다. 앞선 회차에 얼마를 실제로 납부했는지는 별도로 입력받지 않는다.

일정을 구할 수 없는 상태는 `unavailable`, 선택한 공고·주택형·호실을 대조하지 못했으면 `selection_unverified`, 출처 권한이 제한됐으면 `source_restricted`다. 이때도 사용자 자신의 자금 입력을 확인할 수 있다. `null`과 금액 문자열 `"0"`은 화면에서 구별한다.

## 계산 예를 따라간다

합성 예로, 10월 1일 보유 잔액이 5천만 원이고 10월 10일에 400만 원이 들어올 것으로 예상한다고 하자. 10월 20일 분양대금 계약금 7천만 원과 필수 옵션 계약금 100만 원을 내야 한다면 총 납부액은 7,100만 원이다. 확정 자금만 보면 2,100만 원이 부족하다. 예상 자금 400만 원이 입금된다고 가정하면 부족액은 1,700만 원이다. 11월 5일에 들어오는 1억 원은 10월 20일의 결과를 바꾸지 않는다.

원문이 ‘입주 시’처럼 사건만 지정한 납부는 날짜 미정 항목으로 남긴다. 사용자가 지정한 자금의 확정 여부와 공고문에서 검증한 금액·납부일은 각자의 근거를 표시한다. 적용할 호실이 불명확하거나 필수 옵션 금액·날짜를 모르면, 확인한 항목과 아직 확정할 수 없는 총부족액을 함께 표시한다. [호실별 납부 일정의 근거](notice-documents.md)

납부와 유입이 같은 날이면 `beforeIncomingFunds`와 `afterIncomingFunds`가 각각 유입 전과 후의 부족액을 나타낸다. 입금 시각을 모르면 화면에 두 부족액을 함께 표시한다(Q-37). 예를 들어 전날까지 가용 자금이 5천만 원이고 계약금 7,100만 원을 내는 날 400만 원이 입금된다면 입금 전 부족액은 2,100만 원, 입금 후 부족액은 1,700만 원이다. 예상 입금이라면 해당 가정을 표시한다. 보유 잔액의 기준일보다 앞선 납부도 일정에 남지만 그날의 부족액은 보류한다. 기준일 당일 납부가 잔액에 이미 반영됐는지 알 수 없으면 당일과 이후의 누적 부족액도 보류한다. 기준일 당일의 추가 입금은 잔액에 중복해서 더하지 않는다. 화면은 기준일부터 얼마를 납부해야 하는지 표시할 때 `knownCumulativeDueSinceOpeningWon`을 읽는다.

### 강변역 센트럴 아이파크 9월 공고에 대조한다

공고 `2026930040`의 보관된 청약홈 응답과 공식 PDF를 자금표 입력으로 재생했다. 101동 402호의 분양대금은 1,222,020,000원이고 필수 옵션은 21,780,000원이다. 분양대금 계약금 122,202,000원의 납부일은 2026년 10월 23일, 잔금 1,099,818,000원의 기한은 11월 30일로 확인됐다. 필수 옵션 계약금 2,178,000원과 잔금 19,602,000원은 ‘계약 시’와 ‘입주 시’에 납부한다. 합성 보유 자금 1억 원을 입력한 검수에서 총 필요액은 1,243,800,000원, 두 옵션 납부는 날짜 미정으로 표시됐고 날짜별 총부족액은 보류됐다. ## 납부 근거를 저장하고 재사용한다

문서 작업자의 `--live --save` 경로가 공고 수집본과 그때 점검한 일정을 한 트랜잭션에 저장한다. 저장 일정에는 확인한 금액·시점과 문서 식별자·판본·쪽수가 들어간다. 동일한 수집 키로 같은 내용을 재전송하면 기존 수집본을 반환한다. 수집 이후에 읽은 PDF의 다른 판본은 새 수집으로 다룬다.

공고 목록에서 시작한 분석도 허용된 공식 PDF를 점검하면 작업자가 `finish_notice_with_funding`으로 수집본·비교 결과·납부 일정을 함께 저장한다. 임대가 만료되거나 일정이 수집본의 호실·근거와 맞지 않으면 함께 롤백한다. 이전에 일정을 저장하지 않은 수집본에는 이용 가능한 일정이 없다고 표시한다.

사용자가 입력한 보유·추가 자금은 그 분석에만 저장한다. 브라우저는 사용자 JWT로 `funding_entries`를 읽고 쓰며 금액을 십진 문자열로 전달한다. 새 입력은 동일한 요청 키를 재사용하고, 수정은 마지막으로 읽은 갱신 시각을 대조한다. 서울 개발 DB에서 두 임시 계정과 합성 납부 일정으로 2,100만 원·1,700만 원의 입금 전후 부족액, 9,007,199,254,740,993원의 정밀한 재로그인 복원, 타 계정 자금 행 0건과 자금표 조회 404를 확인했다.

예전 수집본에 일정이 없으면 근거를 다시 수집해야 한다. 읽기 권한은 계정과 분석별로 적용하며, 실제 공고·주택형·문서에서 파생한 일정을 표시할 때는 해당 출처의 이용 조건을 다시 확인한다. 자기 분석의 자금과 허용된 일정은 사용자 세션으로 읽고, 응답은 개인 캐시에 보관하지 않도록 `private, no-store`를 설정한다. [수집본과 출처별 보관 조건](ingestion-storage.md)

| HTTP 응답을 받는다 | 화면에서 처리한다 |
| --- | --- |
| 200 | 계산한 금액과 날짜 미정·자료 보류 상태를 함께 표시한다. |
| 400 `invalid_funding_input`, 413, 415 | UUID·주택형·호실과 JSON 본문 형식·크기(4 KiB)를 확인한다. |
| 401 `authentication_required` | 사용자의 로그인 세션을 확인한다. |
| 404 `funding_not_found` | 현재 계정의 분석과 수집본을 다시 선택한다. |
| 503 `backend_unavailable` | 서버에서 근거를 읽지 못했거나 결과 형식을 검증하지 못했다. 재조회를 안내한다. |
