# 한 공고와 주변 단지의 실거래를 비교한다

로그인한 사용자가 선택한 한 분석의 수집본, 주택형, 거래 기간과 검수된 근거를 사용한다. 같은 실행을 다시 열면 당시에 저장한 결과를 반환한다. 공식 자료에서 거래의 공급면적을 확인하지 못하면 그 후보에 보류 사유를 남긴다. [제품 비교 규칙](../prd/01-product-prd.md#72-지역-검색과-비교-규칙)

## 합성 공고 한 건을 재현한다

```sh
python3 scripts/run_analysis_worker.py --demo
```

예시는 2026년 10월 10일부터 31일까지로 사용자가 지정한 기간을 사용한다. 공고 주택형의 확인된 공급면적은 112.400㎡다. 101호의 분양가와 필수 옵션 소계는 7억 1천만 원이고, 102호의 필수 옵션은 미확인이다. 비교 A의 공급면적은 112.50㎡, B는 110.00㎡다. 두 단지가 같은 법정동에 있어 이 범위에서 A, B 순으로 표시한다. B의 분양권과 입주권은 따로 읽는다. 이 예시의 위치·거래·면적 대응은 모두 합성이다. [수집 입력](../../tests/fixtures/ingestion-v0.json) · [단지·면적 대응 근거](../../tests/fixtures/comparison-evidence-v1.json)

## 결과를 조회한다

1. 자기 분석 초안을 만들 때 `conditions_snapshot.comparison`에 선택한 `modelNo`와 필요한 경우 `room`을 넣는다. 예를 들어 `{"comparison":{"modelNo":"01","room":"101동 101호"}}`다. `room`을 생략하면 확인된 호실 소계의 범위와 보류 호실 수를 사용한다.
2. 실행을 접수하고 반환된 `Location`에서 상태를 확인한다. 작업자가 실행을 인수해 비교와 수집본 연결을 마치면 같은 주소에 `/result`를 붙여 GET으로 요청한다. 사용자 세션의 Bearer 토큰을 사용한다. [분석 접수와 취소](analysis-runs.md)
3. 결과 응답의 `analysisId`, `runId`, `snapshotId`, `rulesVersion`으로 당시 분석·실행·수집본·조건에 연결한다. 비교 내용은 `result.contractVersion = "comparison/v1"`에 따른다. 다른 기기에서는 자기 분석의 `latest_run_id`로 해당 주소를 복원한다.

| 응답을 받는다 | 화면에서 처리한다 |
| --- | --- |
| 200 | `result.completeness`는 `complete`, `partial`, `unavailable` 중 하나다. 확인된 가격과 표본 수, 보류·제외 근거를 함께 표시한다. |
| 401 | 사용자 로그인을 다시 확인한다. |
| 403 `comparison_source_restricted` | 소유한 결과에 사용된 자료의 현재 이용 조건으로 표시할 수 없다. 허용 상태를 확인해야 다시 볼 수 있다. |
| 404 `run_not_found` | 계정에서 읽을 수 있는 해당 분석·실행이 없다. |
| 409 `comparison_not_available` | 실행 상태를 확인한다. 아직 진행 중이면 나중에 다시 읽는다. 취소·실패하거나 과거 실행기에 비교 결과가 저장되지 않은 경우에는 새 실행을 접수할 수 있다. |
| 503 | 저장소 응답을 확인할 수 없다. 같은 결과 주소로 다시 조회한다. |

## 가격과 지역의 근거를 읽는다

| 결과 필드를 읽는다 | 사용자에게 설명한다 |
| --- | --- |
| `target`, `conditions`, `noticePrice` | 선택 주택형·면적·허용 범위·기간과 분양가+필수 옵션 소계를 읽는다. 확인된 호실만 가격 계산에 사용한다. |
| `regionDecision`, `appliedScope`, `collections` | 같은 법정동·읍·면을 먼저 판정한다. 필요한 범위·월·출처의 조회와 후보 판별이 끝나 주변 0개를 입증한 때만 구 또는 구 없는 시·군으로 넓힌다. |
| `comparables`, `tradeKinds` | 매매·분양권·입주권을 합쳐 고유 주변 최대 5단지다. 단지별 가장 가까운 공급면적 한 가지의 거래만 종류별 건수·최소·중위·최대로 읽는다. 1~2건은 적은 표본으로 표시한다. |
| `rankingComplete` | 수집이나 동률 판정이 남으면 `false`다. 확인한 후보를 보여주되 최종 순위로 안내하지 않는다. |
| `targetReferences`, `holds`, `exclusions` | 대상 단지 자체 거래, 결론을 유보한 관측과 사유, 근거를 갖춰 제외한 관측을 구분한다. |

금액은 원 단위 십진 문자열이다. 유효 거래가 짝수인 경우 두 가운데 값의 평균이 반 원이면 `medianWon`에 `.5`가 붙는다. `tradeStats.sale`의 매매가격과 두 권리 종류의 신고 거래금액은 따로 표시한다. 권리 신고금액을 프리미엄으로 해석하지 않는다. 호실 가격에는 분양가와 필수 옵션을 분리한 원문 페이지가 들어간다. `noticePrice.heldRooms`로 가격 범위에서 빠진 호실을 확인한다.

기본 면적 허용 범위는 양 끝을 포함한 ±5%다. 확인한 뒤 변경한 경우에만 `areaTolerancePercent`를 십진 문자열로, `areaChangeConfirmed`를 `true`로 전달한다. 직접 지정은 `replacements`에 같은 범위의 `complexId`와 사용자가 교체하기로 한 `replaceComplexId`를 연결한다. 면적 차이 다음 순위는 확인된 단지 좌표 사이의 직선거리다. 동률 등 아직 결정하지 않은 조건이 선정에 영향을 주면 해당 항목에 사유를 표시한다.

## 입력과 결과를 보관한다

현재 실행 API는 분석 초안에 지정한 호실·면적 허용치·교체 요청을 읽는다. 기존 수집본으로 다시 실행하면 그때의 조건을 재사용한다. 완료된 실행의 비교 대화에서는 계약 기간 변경을 제안할 수 있다. 사용자가 승인한 기간은 해당 분석의 새 실행에만 적용한다. [조건 변경 개발 순서](../development-plan.md)

수집한 자료와 지역·단지·면적을 대조한 근거는 별개다. 사용자의 분석 조건은 모델과 호실 등을 선택하는 데 사용한다. 작업자는 서버에서 등록한 근거, 출처·페이지·행 위치와 식별 정보를 해당 수집본에 대조한다. 합성 데모의 대응 자료는 그 버전으로 만든 수집본에만 재사용한다. 실자료 판단에는 출처별 이용 범위와 조사 기록을 적용한다. [대표 단지 실자료 검증](be-05-real-case.md)

공고 번호쌍·회차로 지정한 수집본을 사용한다. 분석에 카탈로그 UUID가 지정된 경우 해당 UUID와 외부 공고·주택형 사이의 연결 근거가 필요하다. 현 버전에서 그 연결을 입증할 수 없으면 `target`과 `noticePrice`는 `null`이고 `holds`에 식별 보류 사유가 남는다. 작업자는 접수 때 등록돼 있던 근거만 사용한다. 실자료의 수집·보강 출처에는 저장·재사용·화면 표시 허용이 모두 필요하다. 허용이 철회되면 소유자가 저장된 결과를 다시 읽을 때도 403을 받는다.

기존 수집본으로 실행하면 같은 저장본을 참조하고 새 실행의 비교 결과를 기록한다. 수집본 연결과 비교 결과, 실행 완료는 같은 DB 트랜잭션에서 확정한다. 작업자가 취소되거나 임대를 잃으면 새 결과를 기록할 수 없다. 사용자 API에서 비교 결과는 `private, no-store`로 응답한다. 개발 실행기는 수집본과 근거를 합친 RPC 응답을 최대 32 MiB까지 읽는다. 이 크기를 넘기는 자료의 분할 처리는 후속 운영 과제다.

## 비교 결과에 질문하고 계약 기간을 변경한다

로그인한 사용자는 비교표에서 “왜 이 거래만 포함됐어?”라고 묻고, “더 알려줘”로 해당 결과에 포함된 거래의 종류·계약일·신고금액을 확인할 수 있다. 답변은 열어 둔 실행의 저장값을 읽는다. 비교 단지 수와 거래 건수를 구분하고, 보류 사유와 출처의 현재 표시 권한을 확인한다.

| 요청한다 | 응답을 사용한다 |
| --- | --- |
| 실행 주소의 `/conversation`에 GET | `analysis-conversation/v1`의 최근 대화 30개를 시간순으로 읽는다. `hasEarlier`는 앞선 대화가 더 있는지를, `previousRunId`는 이 결과를 요청한 이전 실행을 가리킨다. |
| 같은 주소에 POST `{requestId, message}` | 질문을 보낸 뒤 응답을 받지 못하면 같은 요청 UUID로 재시도한다. 비교 기간·지역·대상 거래·보류 사유·호실 소계에 답한다. |
| `/conversation/{turnId}/decision`에 POST `{decision}` | `approve`는 제안한 기간의 실행을 접수한다. `reject`와 `cancel`은 사용자의 결정을 기록한다. 승인된 `proposal.resultRunId`로 실행 상태와 새 비교표를 연다. |

“최근 6개월로 다시 비교해줘”의 기준은 이 분석의 저장된 기준일이다. 제안에는 이전 기간과 새 기간의 시작일·종료일이 표시된다. 실제 수집한 날짜 범위 안에서 “2026-10-24부터 2026-10-26까지”처럼 양 끝을 지정할 수도 있다. 수집 범위 밖이면 `409 conversation_period_unavailable`을 반환한다. 다른 기기에서도 원래 실행을 열면 당시의 비교표, 질문과 결정이 표시된다.

2026-11-23 서울 개발 Supabase에 두 시험 계정으로 로그인해 합성 비교표로 검수했다. 동일한 기간 제안을 동시에 두 번 승인했을 때 새 실행은 하나였다. 10월 24~26일로 다시 계산한 결과에는 24일 분양권과 26일 입주권이 각각 1건 남았다. 재로그인 후 같은 수집본, 이전 결과와 승인 기록을 다시 읽었고 다른 계정의 조회와 승인은 404였다. 휴대전화와 데스크톱 화면 검사는 로컬 브라우저에서 수행했다.
