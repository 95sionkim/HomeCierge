# 내 데이터 관리와 삭제 접수

계정 메뉴 또는 공유 프로필에서 **내 데이터 관리**를 연다. 삭제할 항목을 선택하면 영향을 받는 자료의 종류와 건수를 확인할 수 있다. 마지막 확인에서만 삭제를 요청한다. 계정 전체를 선택하면 확인 문구를 직접 입력해야 한다. 접수번호를 보관하면 로그아웃한 뒤에도 같은 화면에서 진행 상태를 조회할 수 있다. [제품 요구 R-12·A-56](../prd/01-product-prd.md)

## 삭제할 범위를 확인한다

| 선택하는 자료 | 요청 전에 확인할 영향 |
| --- | --- |
| 채팅·분석 | 선택한 채팅이나 분석에 속한 메시지, 실행·비교 대화, 분석별 자금, 저장 보고서와 업로드가 대상이다. |
| 메시지·비교 대화 한 건 | 질문·응답 또는 선택한 메시지와, DB가 해당 입력에서 비롯된 것으로 식별한 제안·실행을 확인한다. |
| 공유 프로필 | 저장한 탐색 조건, 출퇴근 목적지, 연결된 변경 제안과 이력을 정리한다. 다음 맞춤 검색에서 삭제된 조건을 불러오지 않는다. |
| 자금 한 건 | 선택한 자금과 그 금액을 저장한 보고서가 영향을 받는다. 항목별 연결을 확인할 수 있는 보고서는 금액을 제거한다. 영향받는 보고서 수에는 본문을 수정하는 경우도 포함한다. |
| 업로드 한 건 | 비공개 PDF 접근을 차단하고 파일을 정리한다. 예전 수집본의 추출값이 어느 파일에서 나왔는지 확인할 수 없으면 개별 삭제를 보류한다. 분석 전체를 선택하면 해당 범위의 영향을 다시 확인할 수 있다. |
| 저장 보고서 | 선택한 저장본과 그 PDF 다운로드를 제거한다. 원래 분석은 계속 열 수 있다. |
| 계정 전체 | 계정의 입력·분석·파생 자료, 파일, 로그인을 정리한다. 다른 계정의 자료와 공유 공고 목록은 대상에 포함되지 않는다. |

## 접수하고 상태를 읽는다

| HTTP 요청 | 입력과 응답 |
| --- | --- |
| `GET /api/v1/privacy/items?kind=…` | 로그인한 사용자의 항목과 다음 페이지 커서를 읽는다. 다음 요청에는 `before`를 전달한다. 공유 프로필과 계정 전체는 항목 선택이 필요 없다. |
| `POST /api/v1/privacy/impact` | `{scope,targetId}`로 조회 시점의 건수를 읽는다. `reportsDeleted`와 `reportsUpdated`는 저장본을 지우거나 본문에서 항목을 제거하는 건수다. `profileCleared`는 저장 조건·목적지의 삭제 여부, `storageObjects`는 대상 파일 수다. 프로필과 계정의 `targetId`는 `null`이다. |
| `POST /api/v1/privacy/requests` | 최종 확인 후 `{scope,targetId,receiptId,confirmed:true}`를 보낸다. `receiptId`는 새 무작위 UUID v4다. 응답을 받지 못하면 같은 요청과 접수번호로 상태를 확인한다. 즉시 완료는 200, 파일·계정 정리가 남으면 202다. |
| `POST /api/v1/privacy/receipt` | 로그인 없이 본문 `{receiptId}`로 해당 요청의 범위, 상태, 접수·완료 시각과 백업 확인 상태를 읽는다. 접수번호 자체가 조회 권한이므로 URL·분석 로그·브라우저 영구 저장소에 넣지 않는다. |

대상 목록·영향·요청에는 검증된 비익명 사용자 세션을 사용한다. 타인의 항목이나 이미 없는 항목은 404다. 같은 접수번호를 다른 대상이나 범위에 사용하면 409다. 삭제 요청 응답이 끊기면 화면은 같은 번호로 공개 접수를 조회한다. 확인할 수 없으면 번호를 표시해 다시 조회하거나 재시도할 수 있다. 모든 응답에는 `private, no-store`를 적용한다. 접수번호를 가진 사람에게 계정 ID, 파일명·경로, 대화나 금액을 반환하지 않는다. [HTTP 구현](../../src/server/data-deletion.ts)

## 서비스와 백업의 상태를 읽는다

- **처리 중**(`processing`)에는 비공개 파일 정리나 계정 삭제가 남아 있을 수 있다. 화면에 소유 자료가 보이지 않는 것만으로는 삭제 완료를 확인할 수 없다.
- **서비스에서 삭제 완료**(`live_deleted`)는 요청 대상의 DB 처리가 끝났고 관련 Storage 객체가 없어졌음을 확인한 상태다. 계정 전체 삭제는 Auth 계정까지 제거한 뒤 완료한다. 이미 다른 기기에 내려받은 PDF는 해당 기기에 남는다.
- **백업 미확인**(`backup.status=unverified`)이 기본이다. 운영자가 해당 요청의 백업 사본까지 처리된 근거를 따로 확인해야 `verified`와 확인 시각을 기록할 수 있다. 서비스 삭제가 끝나거나 시간이 흘렀다는 이유로 이 값을 자동으로 변경하지 않는다.

2026-11-24 확인한 서울 개발 프로젝트의 요금제는 Free다. Supabase는 무료 프로젝트에 별도 오프사이트 백업을 권장한다. DB 백업에는 Storage의 메타데이터가 담기며 업로드 파일 본문은 별도로 관리된다. 개발 프로젝트와 운영자가 따로 보유한 사본을 모두 포함하는 최종 파기일은 확인되지 않았다. [Supabase 백업 안내](https://supabase.com/docs/guides/platform/backups)

## 중단된 삭제와 복원을 처리한다

개발 작업자는 등록이 확인된 파일 경로만 Storage API로 지운다. 삭제 요청을 다시 받거나 HTTP 응답이 유실되면 DB에서 파일의 부재를 다시 확인한다. 계정 삭제는 개인 자료 접근을 차단한 뒤 파일, Auth 계정 순서로 진행한다. 계정에 연결된 다른 버킷이나 소유관계를 입증할 수 없는 파일이 있으면 해당 접수를 보류한다. 운영자는 접수의 범위를 벗어난 파일을 자동 삭제하지 않는다. [파일 삭제 API](https://supabase.com/docs/guides/storage/management/delete-objects) · [Auth 사용자 관리](https://supabase.com/docs/guides/auth/managing-user-data) · [개발 작업자](../../scripts/process_data_deletion.py)

백업 복원은 사용자 접속과 작업자가 차단된 별도 환경에서 시작한다. 복원 시각 이후의 삭제 요청과 파일 처리를 독립적으로 확인할 수 있으면 해당 삭제를 다시 적용하고, 새 세션에서 입력·파생 결과·파일을 읽을 수 없는지 확인한 뒤 개인 자료를 다시 연다. 과거 백업만 남아 그 사이의 삭제 이력을 입증할 수 없다면 개인 자료를 다시 열 수 없다. 이때는 출처 이용 조건을 확인한 공유 공고 등 복구 가능한 자료만 새 환경에 옮긴다. 백업 사본의 파기와 실제 복원 훈련은 운영 출시 전에 별도로 기록한다.

## 개발 환경에서 확인한 결과

2026-11-24 서울 Supabase 개발 프로젝트에서 임시 계정 두 개와 합성 분석·보고서·비공개 PDF를 사용했다. 로그인한 한 계정에서 같은 자금의 삭제를 동시에 두 번 요청한 뒤 별도 로그인 세션에서 자금이 사라졌음을 확인했다. 승인했던 공유 프로필은 삭제 후 조건과 제안 이력이 비었고, 삭제 전에 보낸 제안을 재전송해도 복원되지 않았다. 다른 계정의 분석에 대한 미리보기와 삭제 요청은 모두 404였다. [실제 Auth·Storage 검사](../../scripts/smoke_data_deletion.mjs)

모바일 브라우저에서 계정 전체 삭제를 확인하자 접수번호와 처리 중 상태가 표시됐다. 이전 세션으로 보고서·파일 조회와 새 채팅 쓰기가 차단됐다. 작업자가 PDF와 Auth 계정을 제거한 뒤 공개 영수증은 서비스 삭제 완료와 백업 미확인을 반환했다. 기존 세션의 토큰 갱신은 거절됐고, 두 번째 계정은 자신의 분석을 계속 읽을 수 있었다. [삭제 접수 마이그레이션](../../supabase/migrations/20261124060304_data_deletion_queue.sql) · [항목별 삭제 마이그레이션](../../supabase/migrations/20261124060511_individual_data_deletion.sql)

별도 PostgreSQL 17에서 두 연결이 동시에 채팅을 수정하고 계정을 삭제하는 경우를 점검했다. 삭제 전 시점의 합성 DB를 격리된 환경에 복원해 자금이 되살아나는 경우를 재현하고, 해당 삭제를 다시 적용한 뒤 새 세션에서 대상 자금이 사라지고 다른 계정의 자료가 보존되는 것을 확인했다. 제공자 백업 사본의 파기는 확인되지 않았다.
